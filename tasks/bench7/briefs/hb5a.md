You do not commit. Your launch prompt says when the `benchmark/` tree is free.

## Why

Bench 7 runs a new node build (upstream main with tn-lmdb storage plus a stack of fixes) on the bench fleet twice: the vote fix always-on (`benchmark/arms/bench7-always.arm`) and adaptive (`benchmark/arms/bench7-adaptive.arm`), 20,000 IOPS disks, the shape of bench 6's run `r20261113-1351`.
The harness already starts the build (faucet allowance, reserved ports, tn-lmdb measures) and knows its seven switches. What it does not know yet is the build's NAMES: `tasks/bench7-contract.md` lists every log line, metric, halt line and hook variable the build adds or changes against main, taken from the code (sections 1 to 6; read it whole: it is your source of truth for every string below; copy strings from it, and where you doubt one, check it in the node tree `/home/drtnarg/coding/telcoin/tn-b7-gate`, read-only).
Three things lose data for good if they are wrong at launch:
- **The teardown keeps only the node log lines that match `benchmark/tools/log-shapes.txt`** (fixed strings, `pull-lib.sh` `bench_logs_prefilter`). A new line that is not in that file is gone after the teardown.
- **The metric export runs while the fleet is up** (`tasks/bench7/orch-prom-export.py`: a must-have list checked per node, then every metric matching a pattern is exported). A metric outside the pattern, or a must-have that is not checked, is gone after the teardown.
- **A node that halts on one of the build's new fail-stops must be seen while the run is live** (`benchmark/node-sampler.sh` counts fatal lines into `fatal_db`; `tasks/bench7/orch-fleet-health.sh` reads the samplers' status lines and alarms).
