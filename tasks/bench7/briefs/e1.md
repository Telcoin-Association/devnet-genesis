## The user's requirement (2026-11-13, verbatim)

> ensure that the closing epoch vote records include the correct state info that contains the closing epoch block info - the record must match the execution data where the closing epoch calls were executed

## What bench 6 found, and what M already does

Bench 6 (`benchmark/private/bench6-r20261113-1351/E-3/findings.md`, first 60 lines): a record's `final_state` IS the block where the epoch-closing calls ran, by construction, and it held at all 37 closes of three runs on every node; but nothing checked it, `final_state` was never logged, and no test asserted it.
The design made on the bench-6 tree: `benchmark/private/bench7-prep/design/design-epoch-record-hardening.md` §A (and §C, §D for tests and units).
**The delta read on M corrects that design and is binding where they differ**: `benchmark/private/bench7-prep/DR-E/findings.md` (verdicts 1 to 3 and 7, and "Changes to the design → E1"). In short:
- M (#1834) already halts, unconditionally, when a STORED record's `final_state` (number and hash) is not the node's closing block: `check_stored_record` / `check_stored_final_state` in `crates/node/src/manager/node/close_epoch.rs` (≈ :712-749, :1265-1284), on the stored close path and at every epoch entry (`run_epoch.rs` ≈ :238 → :590, against the registry's `blockHeight − 1` header). Counter `tn_epoch.final_state_mismatches_total`.
- M does NOT: compare the closing block's own markers; check anything on the BUILD path before the record is saved and voted; log `final_state` on success.

## What to build — no switch

The plan: "extend upstream's guard where it is unconditional". M's guard is unconditional, so the new comparisons extend it without a switch; on a genuine close they hold by construction. This is the one place the rules' "every behaviour change sits behind its switch" does not apply; do not add a `Parameters` field.

1. A pure function `closing_block_check(block: &SealedHeader, epoch, final_consensus, seed: Option<B256>) -> ClosingBlockCheck` (the design's §A signature, adjusted to M's types) that says whether a block is the closing block of `epoch` for the record being built or held:
   (a) the block's `parent_beacon_block_root` equals the record's `final_consensus.hash`;
   (b) the block's nonce carries the epoch (how M encodes it: read the payload builder and the existing re-derive path that already makes (a) and (b));
   (c) the block's `extra_data` is the 32-byte closing marker, equal to the output's shuffle seed when the seed is at hand, 32 bytes long otherwise. On adiri skip (c) for epochs at or below the fork epoch DR-E names (`forks.rs` ≈ :71; read it and state the rule exactly).
   (d) is NOT added: M's entry check already compares against the registry's `blockHeight − 1`.
   The result names which comparison failed, for the log and the counter label.
2. **Build path** (`write_epoch_record`): take the ring's sealed closing header once (DR-E: sample `latest_execution_block()` once at ≈ :411; move the take at ≈ :500-503 above the committee read at ≈ :476) and run the check BEFORE any committee read and before `save_record` (≈ :514). A mismatch: the same shape as M's stored-path halt (an `error!` with the record's and the block's fields, the counter, `Err`): the node stops before it saves, votes on or publishes a record whose `final_state` is not its closing block.
3. **Stored path** (≈ :430-433): run (a), (b), (c) after M's `final_state` comparison (compare `final_state` first so M's existing mismatch tests keep their meaning); the seed from `self.last_consensus_header` when present, length-only otherwise; skip at or below the restored-state floor exactly as M's guard does.
4. **Entry path**: pass the `SealedHeader` M already has (`epoch_start_header`, `run_epoch.rs` ≈ :590) into the guard so (a), (b) and the `extra_data` length are checked at every entry with no new read.
5. **Re-derive path**: add (c) where (a) and (b) are already made.
6. **Logs and counters, always on**:
   - one info line per record a node saves or accepts as its own: message `epoch record published`, explicit `target:` as the file's other lines, fields `epoch`, `final_state` (number and hash), `final_consensus` (number and hash), `digest`, `branch` = `built` | `stored_matched` | `stored_restored` (DR-E: the two publish points ≈ :433 and :519);
   - `tn_epoch.epoch_record_closing_block_check_total{result}` on `EpochMetrics` (`crates/node/src/metrics.rs`; `result` = `ok` or the failed comparison's static name), counted on every path the check runs;
   - `tn_epoch.epoch_close_identity_check_total{result}`: the close-time base-fee identity M already tests silently (`adjust_base_fees`, `run_epoch.rs` ≈ :880-950: canonical tip + 1 == the entered epoch's `blockHeight`), counted `ok` / `mismatch`; do not change what it does on a mismatch.
   If `EpochMetrics`' derive cannot carry a label, use the pattern the file already has for labelled counters or one field per result; say which.
