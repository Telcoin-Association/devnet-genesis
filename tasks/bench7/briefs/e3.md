## Why

Bench 6's finding (`benchmark/private/bench6-r20261113-1351/E-4/findings.md`, the gaps G1 and G2): an epoch the WHOLE network leaves uncertified stops the record collector and the startup sync at that epoch on every node, forever, and a restart does not help; and a conflicting certified record met on the collector path is only logged and asked for again on every pass.
Design: `benchmark/private/bench7-prep/design/design-epoch-record-hardening.md` §B ("Is walking past K safe?", "The walk", "Conflicting certified record") and §C's state-sync tests. **The delta read on M is binding where it differs**: `benchmark/private/bench7-prep/DR-E/findings.md` (verdicts 4, 5, 6 and "Changes to the design → E3"): the stop is at `crates/state-sync/src/epoch.rs` ≈ :343-345; #1841 removed the `requested_epoch >= last_epoch` gate, so the retry can run at the top of each loop; the conflict halt goes at ≈ :279, before `stop_on_local_failure`; M's tests at ≈ :651 and :798 expect today's log-only behaviour and must keep passing with the switches off.

## What to build — two switches, both default off

1. **`epoch_record_collect_past_uncertified: bool`** — the walk. At the stop, with the switch on, when the node holds epoch K as ITS OWN stored, uncertified record (never the epoch-0 dummy, never for a node without that record, never after a `ConflictingRecord` or a local store failure) and fewer than `MAX_UNCERTIFIED_GAPS` = 16 gaps are open: add K to the gap set, count it (`tn_state_sync.epoch_record_gap_walks_total`), log one info line (`epoch record collector walking past an uncertified epoch`, fields `epoch`, `gaps`), and continue with K+1, which is anchored on the node's own record K (its digest and `next_committee`, which come from the node's own execution).
   - The gap set is a `BTreeSet<Epoch>` owned by the collector loop; the startup sync gets its own throwaway set. Every loop iteration retries each open gap with one request; a gap is removed once ANY path stores its certificate (the collector, the node's own vote round, the re-certify path of unit E4).
   - If the node's own K differs from the network's, K+1 comes back invalid with a parent mismatch: the walk stops there as today, and the case is counted (label or a second counter: say which).
   - A node WITHOUT record K (a fresh node, an observer far behind) does not walk: that stays as on M. Document in the function's doc why (K's `next_committee` is not constrained by anything such a node can check).
   - E2's gauge `tn_state_sync.epoch_records_certified_through` must stay right through a walk: it reports the highest epoch with EVERY certificate up to it held, so it stays below an open gap. Add a test.
2. **`epoch_record_conflict_halt: bool`** — the fail-stop. A peer's certified record that validates (anchored on our K−1, carrying a super-quorum certificate) and conflicts with our own stored record for the same epoch: count it ALWAYS (`tn_state_sync.epoch_record_conflicts_total`, switch or not); with the switch on, return `Err` from `collect_epoch_records` so the critical collector task ends the node (and the startup sync fails startup), with an error line that says in plain words that this node's record for epoch K differs from a certified record of the network, that the node has forked, and that the chain data must NOT be deleted before the cause is known. With the switch off: today's behaviour (log, ask again).
   - State in the doc, and in your hand-back for the PR text: the halt repeats on every restart, by design; no single peer can cause it (the evidence is a super-quorum certificate anchored on our own K−1).
3. The switches reach the collector and the startup sync the way PT-0's machinery hands a switch to a component (pt0-api.md); a small `EpochRecordCollectSwitches { past_uncertified, conflict_halt }` value passed in is the design's shape. If the call sites are in `crates/node/src/manager/node.rs`, you edit only those call sites there.
