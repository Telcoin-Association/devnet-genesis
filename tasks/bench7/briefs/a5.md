## Questions (tick each; checkpoint after each)

1. To be checked on the first run, before any table: the numeric fields this build writes on `persisted output`, `output executed` and `output execution task finished` (list them from validator-01's extract; the MDBX fields of a-common §3 are gone), and which series `prom.py` reads are absent from `INDEX.tsv` (bench 6's `tn_engine_persist_wait_seconds`, `tn_engine_unpersisted_outputs`, `tn_engine_commit_interval_seconds`, `tn_node_execution_backlog_outputs` are gone). Name the replacement or write n/a.
2. Per blast and, for B2, per 300-s bucket and per validator: the split per executed transaction: recover, evm, root, finish (`tn_engine_recover_seconds`, `tn_engine_evm_seconds`, `tn_engine_root_seconds`, `tn_engine_finish_seconds`), execute (`tn_engine_execution_duration_seconds`, and the log's `output executed`), persist (`tn_engine_persist_duration_seconds`), save (`tn_reth_persist_save_blocks_seconds`), commit (`tn_reth_persist_commit_seconds`), the task (`output execution task finished`) and the wait; busy ms/s (`tn_engine_busy_milliseconds_total`), queue (`tn_engine_queued_outputs`, `tn_engine_channel_depth`), transactions per output (`tn_executor_output_transactions_count`), executed tx/s (`tn_engine_executed_transactions_total`) and outputs/s (`tn_engine_outputs_executed_total`). Nine validators in B2 (validator-05 on its own row).
3. Is the execution cycle sequential on this base (bench 6's `pipelined_persist` is gone; storage v2 changed the persist path)? Compare, per output, the task time with execute plus persist, and the busy ms/s with their sum; say which and how far apart.
4. What binds in B2: the rate the busy engine allows (busy ms/s over task µs per transaction) against the executed rate, beside the device's write rate against 20,000 IOPS (`metrics.json` `.gcp[<node>].disk_write_ops_per_sec.points`). Bench 6 run 2 and run 3 had the device at 0.998 and 0.999 of 20,000 writes/s with the engines busy 994-996 ms/s, and called that both disk-bound and engine-bound with the device at its limit (report §8.4.1): give both measures and use both words only together.
5. The course through B2: per bucket the commit and save µs per transaction and the executed rate, against the store's size (A6's `disk.json` if it exists, else `tn_lmdb_used_bytes` from the persist CSV); bench 6 run 2's rate fell as its commit went from 54 to 98 µs per transaction (cross-unit notes).
6. The execution spread across validators (`spread.py`): max − min of the execution tips on a 1-s grid per window (B2 with and without validator-05), the dearest engine and which validator lagged in each bucket; the spread is what the always-on form's floor answers to (bench 6 report §4.3), so A9 needs it per run.
7. Output size: transactions per output against the executed rate times seconds per output (rounds per output from the engine lines' `leader_round` span, over `tn_primary_committed_round` per second).
8. The light blasts over the generators' own windows (`light_windows.py`, needs A1's `kpis.json`): executed tx/s per node, outputs/s, the share of empty outputs, busy ms/s, task cost.
9. Signer recovery: the `signers recovered` lines (their `pool=` field is gone) against `tn_engine_recover_seconds`.
