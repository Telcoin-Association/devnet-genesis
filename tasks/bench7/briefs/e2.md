## Why

The user asked whether every node ends up holding every closed epoch's certified record, signer or not.
Bench 6 answered yes for its runs (`benchmark/private/bench6-r20261113-1351/E-4/findings.md`, first 60 lines) but could only show it by joining log lines, and found a false error: eleven own vote rounds logged `failed to reach quorum on epoch close` 64.5 to 65.0 s after the node already held that epoch's certificate from the collector.
Design: `benchmark/private/bench7-prep/design/design-epoch-record-hardening.md` §B "Always on" (and §D). **The delta read on M is binding where it differs**: `benchmark/private/bench7-prep/DR-E/findings.md` (verdicts 4, 5, 7 and "Changes to the design → E2"). Note its path correction: the vote rounds live in `crates/node/src/manager/epoch_votes.rs`, not under the primary.

## What to build — observability only, no switch, no behaviour change beyond a log level

1. **Gauge `tn_state_sync.epoch_records_certified_through`** (`StateSyncMetrics`, `crates/state-sync/src/metrics.rs`; exported as `tn_state_sync_epoch_records_certified_through`): the highest epoch E such that this node holds a certified record for every epoch 0..=E. Set wherever the node learns a certificate (the collector, the startup sync, its own vote round reaching quorum): find the one place all three pass through, or set it in each; say which. It must be right after a restart (set from the store at start). An absent record 0 reads as "none": say how the gauge shows that (the design's choice; keep it).
2. **`peer` and `signers` on the `retrieved cert` lines** (`crates/state-sync/src/epoch.rs`, the collector and the startup sync): which peer served the certificate and how many signers it carries. `request_epoch_cert` drops the responder today (`crates/consensus/primary/src/network/mod.rs` ≈ :2770-2797): make it return the responder alongside the certificate; its callers are `state-sync/src/epoch.rs` ≈ :264 and `crates/node/src/manager/epoch_votes.rs` ≈ :265. Keep the wire format and the validation untouched: this is a return value, not a message change.
3. **The false quorum error** (`crates/node/src/manager/epoch_votes.rs` ≈ :231-237): before logging `failed to reach quorum on epoch close` as an error, check whether the certificate is already held (`cert_by_digest`, as DR-E names it); if it is, log one info line instead (message `epoch vote round ended without own quorum; certificate already held`, fields `epoch`, `digest`, `source` if known) and count `tn_node.epoch_vote_round_superseded_total` with the file's existing `metrics::counter!` pattern. If it is not held, the error stays exactly as it is. Nothing else in the vote round changes: same timeouts, same failsafe, same return value to the caller unless the caller only used it to log.
