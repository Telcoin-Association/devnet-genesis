## Why

The user's requirement (2026-11-13): "every node should have every closing epoch record at quorum - even if it didn't sign".
Bench 6 found the one way that fails (`benchmark/private/bench6-r20261113-1351/E-4/findings.md`, gap G1): an epoch whose vote round gave up on every node (votes for one record split across rounds that never overlapped, or too few members up at the close) stays uncertified forever: the close-time failsafe re-votes only epoch N−1, once.
The delta read on M (`benchmark/private/bench7-prep/DR-E/findings.md`, verdicts 4 and 6, "Changes to the design → E4") confirms it on main and adds why it matters more than it looks: every pack path needs a stored record of the epoch, a fresh node only gets certified records, so a network with one never-certified epoch may not be able to bring up a new node past it. **Re-certifying is the only fix for such a node.**
Design: `benchmark/private/bench7-prep/design/design-epoch-record-hardening.md` §B "Getting K certified later" and §C's `epoch_votes` tests. DR-E's anchors on M (`crates/node/src/manager/epoch_votes.rs`: the failsafe ≈ :483-502, the startup re-arm ≈ :563-578; the per-epoch vote dedup in the primary's handler ≈ `handler.rs:889-901` and `start_epoch.rs` ≈ :1141) are from before unit E2's edits: `grep -n` on your base.

## What to build — one switch, default off: `epoch_record_recertify: bool`

1. **R1, `RetainedEpochVotes`**: keep the VERIFIED signatures per (epoch, record digest) across vote rounds, and seed a new round for the same (epoch, digest) with them, so two rounds that each fell short can add up to a quorum. Drop an entry when a certificate for that epoch is stored (by any path) or the epoch leaves the lookback. A `parking_lot` mutex never held across an `.await`; bounded by the lookback × committee size; no hashing order in anything that reaches a certificate (the aggregated signature's signer set must be built in the same canonical order M uses today: find it and reuse it, do not re-implement).
2. **R2, the re-vote**: with the switch on, the close-time failsafe re-votes N−1 as today PLUS one older record of the node's own that is still stored uncertified, picked round-robin by N within the last `MAX_RECERTIFY_LOOKBACK` = 16 epochs; the startup re-arm does the same. Concurrent rounds stay at 3 or fewer (the design's bound against the 5-queue eviction ≈ :403-405: verify the number on M and say what it is).
   - Who signs: only a node that holds K uncertified and whose key is in K's committee; the BLS vote is the same deterministic vote as the original (same message, same domain): **no new message type, no wire change**.
   - Receivers check each vote against their OWN record K, as M's handler does today (former committee members may still sign their epoch's record: intended; cite M's line).
   - The per-epoch dedup on the receiving side (one vote per author per epoch): establish whether it lets a re-vote of an old epoch through on M as it is, and if it does not, what the smallest change is; that file (`crates/consensus/primary/src/network/handler.rs`) is NOT in your list: if it must change, stop that item and hand back the exact need (another unit may hold the file).
3. With the switch off: byte-identical vote rounds (M's tests untouched and green); `RetainedEpochVotes` is not consulted.
4. Counters (inline `metrics::counter!`/`gauge!` in the file's existing `tn_node.*` style): `tn_node.epoch_record_recertify_rounds_total{result}` (`certified` | `short` | `skipped`), `tn_node.epoch_record_retained_votes` (gauge: signatures held across rounds). One info line per re-vote round started (`epoch record re-certify round`, fields `epoch`, `digest`, `retained`, `needed`).
