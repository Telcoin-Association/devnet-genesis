# Bench 7 analysis: decisions the orchestrator took on the units' questions (read by the comparison units and the report writers)

Each line: the question, the decision, who asked. Nothing here is a figure; figures are cited from the units' files.

- Arms summary rows (KPI analysis, run 7a): `arms.json` has no row for blast 1 when no second of it has all ten generators in their mixed phase, and its blast-2 row ends at the kill. No row is added and the tool is not changed during the analysis; a unit that needs blast 1 or the part of blast 2 after the kill extracts it itself and says so.
- Rejoin mark of validator-05 (certification analysis, run 7a): the certification analysis keeps its own mark (the first `cvv_active` sample of `tn_node_mode`); the recovery analysis's `recovery.json` is the source for the rejoin time itself wherever a text states it. In run 7a both fall after blast 2's end, so no blast-2 figure depends on the choice.
- "First 120 s" of blast 2 (certification analysis, run 7a): the comparison of run 7a with run 7b uses the common brief's definition (from the start of the mixed phase); the comparison with bench 6 uses bench 6's definition (from the start of the warm-up), because bench 6's figures were made that way. Each table names which one it uses.
- Budget: the first units used 260-270k tokens against a 200k budget. Later units reuse the first run's script copies; a unit past 200k finishes its current question, checkpoints and hands back.
- Distance between the tip and the named block (per-header analysis, run 7a): bench 7 counts it by rank among block-bearing outputs, not by the difference of consensus numbers as bench 6 did (this build's block-bearing outputs are spread thinly over the consensus numbers); the old measure is kept as `tip_minus_named_consensus_numbers`. The bench 6 comparison applies the bench 7 definition to bench 6's runs where it compares distances, or names the definition beside each figure.
- Holders after validator-05's start (per-header analysis, run 7a): validator-05 is counted as a voter that does not hold the named block (it ran hundreds of outputs behind until after blast 2), in both runs alike; a text that gives a holder count or an "at most five other voters" share for that window says so. No second set over eight voters is made.
- Validator-05's tip after its start is taken from its own `output execution task finished` lines when its last header line is more than 5 s old (`exec_tips.py`; rows marked in `vt_src`); the same stand-in is used on run 7b.
- Window "B2-postrejoin" (disk analysis, run 7a): not re-run. In run 7a validator-05's rejoin falls after blast 2's end, so the window is empty; the window after validator-05's start stands in and is named as such. If run 7b's rejoin falls inside blast 2, its units give the window and the comparison says the other run has none.
- Validator-05's restart lines (the consensus pack's WAL replay, torn epoch-store tails, the static-file unwind) are quoted in the disk analysis (`A6/disk.md` §7) and not counted anywhere; the recovery analysis owns the recovery's timeline, and a text that names those lines cites the disk analysis.
- The first process of every node (recovery and census analysis, run 7a): each node's first process, started during the deploy, ran a few minutes with every switch at its default before the coordinated start under the arm; no epoch closed and no blast ran before the arm. The report says this in one sentence in its run facts, for both runs (the same harness step), with the times from each run's census.
- "Kill to `CvvActive`" against bench 6 (recovery analysis, run 7a): not compared as one number. The kill came later into the load in bench 7's shape as it ran (more load left after it), so the bench 6 comparison gives, side by side, the kill's offset into blast 2, the load left after the kill, the kill-to-promotion time and the time from the load's end to the promotion, and says the runs differ in the first two. Between runs 7a and 7b the comparison gives the same four, with the kill's closing epoch (5 and 4).
- Lost own headers, two kinds (loss analysis, run 7a): the briefs' definition (a header proposed with no quorum) misses the commit-path kind: a header that was certified but never committed, whose digests the proposer re-queues with `digests resent cause=committed`. Every preamble loss of run 7a was of that kind. The loss analysis counts both kinds on both runs and names them apart ("not certified", "certified, not committed"); `lost_own_headers` of the certification analysis stays the first kind only and says so.
- "Landed" against "seen" (loss analysis, run 7a): a landing's time is its block's timestamp; a sighting's time is when the generator's scanner saw it. `longest_zero_own_landed_in_mixed` is by block time, so it does not contradict sightings minutes later of transactions in blocks stamped seconds after the kill. The loss analysis checks the block timestamps of generator 05's late sightings in the block map and says which it is.
- Certified-through gauge at the end (epoch analysis, run 7b): compared with the last epoch closed INSIDE the export (epoch 5 in run 7b; a later close at 19:25:01Z is outside the export and partly outside the logs, which were pulled from the nodes before it on three validators). The row says so.
- Windows of the engine analysis: the common brief's (B0, B1, B2 = the mixed phase), not bench 6's `[warmup.end, mixed.end]`; the bench 6 comparison recomputes bench 6's engine figures on the common brief's windows where it compares them, or names the difference beside the figure.
- "What binds" (engine analysis, run 7a): no text calls a bench 7 run "disk-bound" or "engine-bound" in one word. It gives the two measured things side by side: the engine's busy time per second and what share of its time per transaction is persist; and the device's write count against its cap with the device time per write. The disk analysis owns the device reading, the engine analysis the engine's.
- Rejoin mark, corrected rule (certification analysis, run 7b): the mark is the first `cvv_active` = 1 sample AFTER a 0 following the start (a start-up sample can read 1 before the node sets its mode). Run 7a's mark agreed with its own log line to 20 s and is not re-made.
- Far validators' generators (KPI analysis of run 7b, loss analysis of run 7a): in both runs the generators of validators 02 and 06 land about a tenth of the others' transactions in the light blasts. The loss analysis of each run owns the explanation (key `far_generators`); the bench 6 comparison says whether bench 6's runs 2 and 3 show the same (their per-generator KPIs exist), because that decides whether it is new with this build.
