# Bench 7 report: r20261115-1131 (always-on) and r20261115-1653 (adaptive) at 20,000 IOPS

Two fleet runs on 2026-11-15 on one build, node commit 91a15e223 (image `adiri@sha256:15acdccafff7…68822c`), with ten validators and one observer, each node on a 100 GB Hyperdisk Balanced at 20,000 IOPS [RF 7a] [RF 7b].
Run 7a ran the always-on vote form and run 7b the adaptive form, the arms' only difference (`quorum_exec_block_starved_rounds` 0 and 4); both ran with the order hold and the three epoch-record switches on, and with the closing-block check, which has no switch [RF 7a] [RF 7b] [orch l.99].
Read next: the form comparison, `benchmark/private/bench7-r20261115-1653/A9/comparison.md`; its recommendation, `benchmark/private/bench7-r20261115-1653/A9/recommendation.md`; the bench 6 comparison, `benchmark/private/bench7-r20261115-1653/A10/vs-bench6.md`.
One run stands in each cell throughout: a difference inside run 7a's own spread is not told apart from noise, and no row carries a significance test [C recommendation].

## 1. Summary

### The form

The form comparison's recommendation to the repository owner, who decides, in its own words [C recommendation]:

> The two runs support keeping the always-on form as the default at 20,000 IOPS: on blast 2's throughput, fleet certification and round rate the forms are not told apart from run 7a's own spread, and the rows outside that spread show the adaptive form naming a fresher block, whose value bench 7 did not measure, with a higher seen p95 and a lower blast-0 rate; it also held more headers and adds code the always-on form does not carry.
> The support is weak: one run of each form on the same build and the same disk, with per-validator rows that move in both directions.

### What bench 7 shows

- On blast 2's chain rate, seen p50, fleet own-header certification, lowest validator and committed-round rate the two forms are not told apart from run 7a's own spread; blast 2's seen p95 and blast 0's rate lie outside it against the adaptive run, and the per-validator rows outside it move both ways (§4.1) [C Q1.01] [C Q1.05] [C Q1.09] [C Q1.10] [C Q1.24] [C Q1.06] [C Q1.04] [C q5_per_validator.outside_7a_bucket_range].
  Under load 61.5 % of the headers run 7b built over blast 2 lay inside its starved window, and 38.51 % of its headers named the author's tip against 0.26 % in run 7a [C Q4.26] [C Q4.17].
- In blast 2 lost own headers carrying batches still occurred in both runs on all nine validators other than 05, and no gap resend followed any of them, where in bench 6 every gap-resend second of those generators fell 280-345 s after one (§4.2) [V q2_senders a, b] [V q3_hold a, b].
  Run 7a's blast 1 is the exception: one gap episode of 4 transactions on generator 06, whose resend second followed a lost own header of validator-06 in bench 6's pattern, and 22 `nonce_too_high` skips counted by the export, 2 per node on 11 nodes [C Q2.14] [V q3_hold a] [C Q2.06].
- The hold held 1,866 headers over blast 2 in run 7a and 3,259 in run 7b, none carrying a batch, and held headers certified 49.8 % and 60.5 % of the time against 97.3 % and 97.4 % for the rest, an association no counter ties to the hold (§4.2) [C Q3.36] [C Q3.37] [C Q3.61] [C Q3.62].
  The one counter that isolates the hold, its out-of-order re-queue count, has no bench 6 twin, so the senders' fall against bench 6 is not separable from the storage engine, the vote path and the run's shape [V q3_hold.attribution].
- Over all of blast 2, 10.31 % of run 7a's headers and 12.55 % of run 7b's were under-held (at the proposal at most five other voters held the block they named), and those certified 61.25 % and 66.70 % of the time against 99.53 % and 99.06 % for the rest (§4.3) [7a A3 q4u B2.fleet] [7b A3 q4u B2.fleet].
  No counter divides the fall in certification against bench 6 between the vote-handler rework, the voters' execution lag, the hold, the adaptive rule change and the run's shape [V q3_certification_rounds.attribution].
- The engine and the device both sit below their limits, the engine nearer to its own: it executed 9,293 / 9,376 tx/s per node (log, mean per node) against the 9,500 / 9,582 tx/s its task cost allows at full busy, persist 47 % of the task's time per transaction, while each device write took 8.50 / 8.67 ms (§4.4) [7a A5 window.2.bound_check] [7b A5 window.2.bound_check] [V q3_storage.runs.<run>.engine_b2] [V q3_storage.runs.<run>.disk.b2].
  Through blast 2 the store grew and commit per transaction rose with it, from 21.49 to 42.07 µs in run 7a, while the executed rate fell from 10,470 to 8,393 tx/s [7a A5 course.buckets].
- Every batch-carrying header of the far validators 02 and 06 was certified in both light blasts of both runs, 46 to 76 % of them were never committed, and their batches took 12.9 to 61.4 s at the median from first own proposal to execution against 0.93 to 1.37 s on the near validators (§4.5) [V q3_far_validators B0.bh_cnc_share, B1.bh_cnc_share] [C Q3F.06, Q3F.16].
  The hold held none of their headers and bench 6, without a hold, shows the same pattern in blast 0; the cause is open, and its last step, near headers not naming the late certificate, is inferred because which parents a header names is not logged [C Q3F.10, Q3F.20] [V q3_far_validators B0.bh_cnc_share].
- Run 7a closed 8 epochs and run 7b 7, each on one record hash and one closing block, and the closing-block check returned `ok` 179 and 135 times fleet-wide (§4.6) [C Q1.36] [7a A4 closing_block_check] [7b A4 closing_block_check].
  Run 7b's last close lies outside its export, so its 6 closes published by all eleven nodes are not like for like with run 7a's 8; the conflict, re-certify and walk paths never fired on any node, so the runs do not exercise them [C Q1.36] [7b A4 closes[6].published_nodes] [7a A4 collector, vote_rounds] [7b A4 collector, vote_rounds].
- Validator-05 reached `CvvActive` again in both runs after replaying the kill's epoch (95.4 s and 68.2 s) and one rejoin attempt, and no other validator left `CvvActive` (§4.7) [7a A4 recovery replay_of_epoch5_s, rejoin_attempts, left_cvv_active_outside_v05] [7b A4 recovery replay_of_epoch4_s, rejoin_attempts, left_cvv_active_outside_v05].

### What did not happen

- No fail-stop phrase the census counts, among them a refused closing block, a conflict halt, a fork, a fatal database failure and an output gap, on any node in either run (§4.8) [7a A4 census fail_stops, arms_agreement.fail_stop_nodes] [7b A4 census fail_stops, arms_agreement.fail_stop_nodes].
- No closing-block result other than `ok` and no close-identity `mismatch`; the check's failure labels have no series on any node (§4.6) [7a A4 closing_block_check, close_identity_check] [7b A4 closing_block_check, close_identity_check].
- No store failure signal: `fatal_db=0` on 11 of 11 nodes at both runs' end checks (§2) [RF 7a] [RF 7b].
- No out-of-order re-queue: the hold's counter read 0 in the log, the warnings and the export of both runs (§4.2) [C Q3.49] [C Q3.50].
