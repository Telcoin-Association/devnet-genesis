## 2. Run facts and provenance

### Build and harness

- Node image `adiri@sha256:15acdccafff7…68822c`, the same digest in both runs, built from node commit 91a15e223, version 0.1.0 with the `faucet` feature [RF 7a] [RF 7b].
  91a15e223 is the top of the bench 7 stack: upstream main 45dce8947 plus 114 commits [orch l.8] [orch l.736].
  The manifest names the storage engine `tn-lmdb` in both runs [RF 7a] [RF 7b].
- The arm sets seven node switches through the prestart step, before the coordinated start [RF 7a] [RF 7b]: `quorum_exec_block`, `vote_queue_fix`, `digest_order_hold`, `epoch_record_collect_past_uncertified`, `epoch_record_conflict_halt` and `epoch_record_recertify`, all true, and `quorum_exec_block_starved_rounds`, 0 in run 7a (arm `bench7-always`) and 4 in run 7b (arm `bench7-adaptive`).
  The starved-rounds value is the only difference between the two arms [RF 7a] [RF 7b].
  The closing-block check has no switch; it ran in both runs [orch l.99].
  A later form of the stack drops `epoch_record_conflict_halt` and its threshold (head 04 rebuilt without them, `b7/n04`) [orch l.964] [orch l.1004]; bench 7 ran with the switch on.
- Generator image `sha256:7cefcc50…5a59`, commit 62bbd5f, the commit bench 6's run 2 used [RF 7a] [V q1_same_shape pairs.always.equal].
- Harness at deploy: d8483104c39c for run 7a and 2ff39153a9d0 for run 7b, each dirty only under `tasks/`, with `benchmark/` at its last commit [RF 7a] [RF 7b].

### Fleet

- Ten validators and one observer, `c3-highcpu-8`, one 100 GB Hyperdisk Balanced per node at 20,000 IOPS and 800 MiB/s, boot image `ubuntu-2404-noble-amd64-v20261105` [RF 7a] [RF 7b].
- The bench 6 comparison finds the zones, the machine, the disk, the generator, the epoch length (1,200 s) and the consensus parameters equal between run 7a and bench 6's run 2 [V q1_same_shape pairs.always.equal].
  Validators 01 to 10 are in us-west2-a, europe-west2-b, australia-southeast1-c, asia-northeast1-b, us-east4-b, europe-west4-a, asia-southeast1-b, asia-east2-a, asia-northeast3-a and asia-south1-c; the observer is in us-west2-a [V q1_same_shape facts.b6r2.zones_used].
- Ten generators, one per validator: generator NN sends to validator NN [7a A1 per_generator.target].
- The host probe was uniform in both runs (kernel 7.0.0-1017-gcp, read-ahead 128 KiB) [RF 7a] [RF 7b].
  Fsync probe medians were 1,044 µs in run 7a and 1,074 µs in run 7b, with no node flagged slow [RF 7a] [RF 7b]; bench 6 flagged two nodes slow in each of its runs 2 and 3 [V q1_same_shape facts.fsync_slow].

### What differs between the two runs, and against bench 6

One run each [V q1_same_shape facts.<run>]:

| | run 7a | run 7b | bench 6 run 2 | bench 6 run 3 |
|---|---|---|---|---|
| idle from the deploy's end to the blast's launch, min | 15.7 | 5.7 | 1.2 | 0.7 |
| the kill's closing epoch | 5 | 4 | 4 | 4 |
| the kill, s into blast 2's mixed phase | 817 | 1,121 | 1,477 | 1,393 |
| load left after the kill, s | 1,608 | 1,290 | 950 | 1,017 |
| blast 1 in all, s / its mixed phase, s | 1,278 / 954 | 748 / 374 | 946 / 408 | 999 / 449 |
| transactions queued in a pool at blast 2's start | none | none | 36 (v04), 682 (v06) | 831, 575, 681, 266, 147 (v06-v10) |
| each node's first process at switch defaults, min | 3.2-7.8 | 3.2-7.5 | 3.1-7.3 | 3.1-7.7 |

- The idle is the schedule, not the form: in both runs the idle check stopped the chain and the blast was launched by hand (§5), after 15.7 min in run 7a and 5.7 min in run 7b, so validator-05's kill fell in closing epoch 5 in run 7a and in closing epoch 4 in run 7b [V q1_same_shape facts.idle_deploy_to_blast_min] [C Q1.37].
- Both bench 7 runs killed validator-05 earlier into the load than bench 6 did, so more load was left after the kill: 1,608 and 1,290 s against 950 and 1,017 s [V q1_same_shape facts.load_left_after_kill_s].
  The two runs' "before the kill" windows therefore have different lengths, 817 s and 1,121 s [C Q1.38].
  The outage lasted 300 s and the observer restarted 300 s after validator-05's start in all four runs [V q1_same_shape facts.outage_s, facts.start_to_observer_restart_s].
- Run 7a's blast 1 is the longer one; in it, generator 06's preamble wait ran its full 600 s (13:02:05-13:12:05) after 737 preamble transactions of 67 senders were lost at 13:02:36 [7a A1 preamble.json blasts.1.by_generator.06].
  No generator lost preamble steps in run 7b [RF 7b].
  So blast 1 of run 7a has no second with all ten generators in their mixed phase, and §3 gives it over the nine other generators' common window, 342 s [C Q1.03].
- Every node's first process, started during the deploy, ran with every switch at its default before the coordinated start under the arm, and each node had two processes before blast 0, in all four runs [V q1_same_shape facts.<run>.first_process_defaults]; no epoch closed and no blast ran before the arm.
- Bench 6 started blast 2 with transactions still queued on two validators in run 2 and on five in run 3; neither bench 7 run had any [V q1_same_shape facts.<run>.blasts[2].pool_at_start_nonzero].

### Prometheus is partial; what stands in

Run 7a:

- Validator-09's series are partial for the whole run: its metrics agent lost one remote-write batch of every scrape, while the node itself was healthy and its logs are whole [RF 7a].
- Not in Prometheus for validator-09: `up`, `scrape_*`, `tn_engine_root_seconds`, `tn_executor_output_transactions`, `tn_primary_vote_stage_seconds`, `tn_primary_uncertified_report_dropped_total`, `tn_reth_persist_save_blocks_seconds`, `tn_storage_tndb_write_stall_seconds`, `tn_worker_batch_report_seconds`, `tn_worker_batch_size_bytes`, three `reth_storage_providers_database_*` series and two `reth_trie_*` series [RF 7a].
  A figure over validators from one of these covers nine validators and says so.
- Restarting the agent on validator-09 at 12:37:50 changed nothing [RF 7a].
- What stands in: an end-of-run snapshot of validator-09's own metrics endpoint at 14:23:07, and one of validator-08's for comparison, cumulative since the process started at 11:59:06 [RF 7a].
  They give whole-run totals of every counter and histogram, with no time series.
- The export covers 11:46:38-14:27:13 at a 15-s step, 397 metrics and 22,504 series; of its 38 must-have checks, 27 are ok, 4 lazy, 4 absent because nothing was counted and 3 incomplete, all three validator-09 [RF 7a].

Run 7b:

- Prometheus is partial on three validators and the observer; the orchestrator's first note named two, and the engine and disk analyses corrected it [RF 7b] [7b A6 export_coverage]:
  - validator-01 lacks four series for the whole run, among them `tn_engine_persist_duration_seconds` and the consensus store's write-stall series;
  - validator-05 lacks three series until 18:40:00;
  - validator-08's `tn_engine_queue_wait_seconds`, `tn_executor_output_transactions`, its write-stall series and three other executor and reth series stop at 18:29:45;
  - the observer's save, commit, persist-duration and write-stall series stop at 18:58:45.
- The export covers 17:08:30-19:19:50 at a 15-s step, 397 metrics and 22,759 series; its check reads 29 ok, 3 lazy, 4 with nothing or almost nothing counted and 1 incomplete (validator-01's persist duration) [RF 7b].
  The check asks only for any sample in the window, so a series that stops mid-run passes it.
- What stands in, for every node: per-minute samples of each node's own metrics endpoint, about 5,100 series a node, all 11 nodes at 17:46:24 and then every 60 s from 17:46:32 to 19:19:36, 94 rounds [RF 7b].
  Validator-05 has no sample in the five rounds of its outage (18:44:37-18:48:36), and its counters restart from zero at its start [RF 7b].
  Counters and histograms are cumulative since the process started, so the difference of two samples is that window's total.
  The engine analysis lists every cell it took from the samples, and checked them against validators the export holds whole: within about 1 % over whole windows, up to about 5 % in 300-s buckets [decisions l.28] [7b A5 .run.r20261115-1653.stand_in].
- The sampler ran one `curl` of each node's exporter over ssh per minute, against the agent's four scrapes a minute; nothing else touched the live fleet besides the harness [RF 7b].
- Run 7a has only its two end-of-run snapshots, so a per-minute figure exists for run 7b only, and run 7a's stand-in for validator-09 is a whole-run total.

Both runs:

- On every node the agent's target label `network` replaces the node's own `network` label (`primary`, `worker-0`), so about 910 series pairs collapse into one, about 110 of them with different values (the `tn_network_*` per-network counters) [RF 7a] [RF 7b].
  A per-network figure cannot be read from Prometheus in either run; run 7a's snapshots and run 7b's samples keep both labels.
  This is not new in bench 7 [RF 7a].
