## 6. Open questions and what a next run could test

Each item: the question, what would answer it, and the section it comes from.

1. Would a second run of each form keep the recommendation?
   Run 7a's spread is variation inside one run, not between runs.
   Rows inside it could flip: fleet certification (spread 93.37-97.29 %) [C Q1.09], the lowest validator (55.2-89.3 %) [C Q1.10], rounds with four or more under-held headers (0.0-27.9 %) [C Q1.28] and committed rounds per second [C Q1.24]; the two rows against the adaptive run, blast 2's seen p95 and blast 0's rate, could fall inside a second run's spread [C Q1.06, Q1.04].
   A second run of each form on the same build and disk answers it (§4.1).
2. The 50,000 IOPS disk.
   Bench 6 found the adaptive form ahead on certification there and behind on the senders' cost; bench 7 made no run on it, so which cost counts more stays open there (§4.1).
   A pair of runs at 50,000 IOPS on this build answers it.
3. What the named block's age costs.
   Bench 7 measured the distance from the tip to the named block, 7.57 / 4.83 block-bearing outputs [C Q4.21], and a lower bound on the block's age, 7.36 / 4.43 s [C Q4.23], but not what that age costs (§4.1).
   If the age costs something, the fresher block is a reason to make the adaptive form the default.
4. The floor at 16 outputs against 8.
   The per-header analysis's arithmetic predicts no under-held header in either run at a floor of 16 [7a A3 perheader floor] [7b A3 perheader floor]; that is arithmetic on these runs, and only a run at the deeper floor tests it (§4.3).
5. What lowers the far validators' committed share.
   In blast 1 bench 7 committed 2.12-3.50 % of the certificates of validators 02 and 06 against bench 6's 3.96-6.49 % [V q3_far_validators B1.committed_share_pct], and no counter isolates the vote-handler rework, the near validators' speed on the new storage engine or the round rate (§4.5).
   A field on `header proposed` naming the parents a header names would turn the inferred last step of §4.5 into a measurement; the far validators' missing leader slots in blast 1 [V q3_far_validators B1.leader_share_pct] would need the schedule's reputation scores logged beside them.
6. What separates the upstream vote-handler rework from the hold's cadence.
   Both moved together in both bench 7 runs, so the fall in certification and the hold's cost are not separable between them (§4.2, §4.3).
   One run with the hold switched off and one without the rework, on this build, would separate them.
7. The hold's early-trigger candidates are inferred, not measured (§4.2).
   The review proposed a field for the un-held count on the header line; with it, a run would count them.
8. The engine's sequential cycle as the ceiling.
   Bench 6's statement that at 50,000 IOPS the engine's sequential cycle sets the ceiling cannot be tested on bench 7: both runs were at 20,000 IOPS, where the engine was busy 978.1 / 978.4 ms per second and the device ran at 0.8591 / 0.8628 of its write cap [V q7_statements 4.6 line 60].
   Bench 6's statement that a faster configuration (a faster disk, pipelined persist, group commit) widens the engines' spread is listed as untestable too [V q7_statements 4.3 line 386] (§4.4).
   A run at 50,000 IOPS on this build answers both.
9. The two recovery items measured and not explained (§4.7).
   Validator-05's first own certificate after its promotion committed after 1.65 s in run 7a and 59.6 s in run 7b [7a A4 recovery own_after] [7b A4 recovery own_after]; the parents field of item 5 would show whether the near validators named its first certificates.
   Validator-04's 516 spawn-capacity errors as epoch 5 began in run 7b are counted by task (vote requests and gossip processing lead) but not explained [7b A4 census leads.spawn_capacity]; a gauge of the spawner's tasks in flight would show what filled it.
10. The metrics agent's defect.
    Validator-09's Prometheus series in run 7a and two validators' in run 7b are partial: the agent lost one remote-write batch of every scrape [RF 7a] [RF 7b].
    The units used per-minute endpoint samples as stand-ins (§2, §5); fixing the agent before the next run removes the need.
11. The switches nothing triggered.
    The conflict evidence, the re-certify round and the walk past an uncertified epoch were on in both runs and never fired (§4.6).
    The e2e tests cover them; the fleet did not, and a fleet run that injects a conflicting record or withholds a record's certificate would exercise them under load.
