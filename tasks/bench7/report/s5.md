## 5. Friction and harness

### What cost fleet time

The first attempt at run 7b, `r20261115-1450`, was lost to an expired cloud login [O 16:45Z].
It was launched at 14:50Z, 3 h 20 min into a login of about 11:28Z that lasted just under 5 h [O 16:45Z].
Its chain stopped at the idle check at 16:04:23Z, and its blast segment was launched by hand at 16:08:08Z [O 16:10Z].
At about 16:24Z, 16 minutes into the blast segment and during the first light blast, the token could not be refreshed: "Reauthentication failed. cannot prompt during non-interactive execution" (the blast log's line 411) [O 16:45Z].
The driver stopped with rc 1 ("== blast15 rc=1 2026-11-15T16:40:25Z"), and its own message named the light blast's arm, not the credentials [O 16:45Z].
Blasts 1 and 2, the load blast with the kill, never ran [O 16:45Z].
The nodes stayed healthy, but the fleet of 22 instances stayed up with no way to tear it down until the owner logged in again at about 16:41Z [O 16:45Z b].
It was torn down at 16:53:02Z: 22 instances deleted, none left [O 16:55Z].
The re-run, `r20261115-1653`, launched at 16:53:25Z on a fresh fleet, with the same image digest and an env identical but for the run id [O 16:55Z] [RF 7b].
The attempt cost about two hours of fleet time; it is not a bench 7 run, and no figure in this report comes from it [L 2026-11-15] [RF 7b].
The rule made from it: a fresh login before every fleet launch, deploy or blast, unless the last one is under an hour old, because a run needs about three hours of valid credentials (deploy 53 min, blast 102 min, export, teardown and archive 25 min) [L 2026-11-15].

### The metrics agent loses one batch per scrape on some nodes

The orchestrator read the cause from validator-09's agent config during run 7a [O 14:28Z].
The vendored agent scrapes the node, sets `network` to the chain's name on every series, and remote-writes the result [O 14:28Z].
That overwrites the node's own `network` label (`primary` or `worker-0`), so about 910 series pairs get identical label sets and timestamps, about 110 of them with different values [O 14:28Z].
Inside one remote-write request Prometheus drops the second of a pair silently [O 14:28Z].
When a pair with different values straddles the boundary between two 2,000-sample batches, the later request meets a committed sample ("duplicate sample for timestamp; existing 0, new value 1") and Prometheus rejects that whole batch, on every scrape [O 14:28Z].
Which batch is hit depends on the order in which the node process exposes its series, which is hash order per process, so it changes when the process restarts [O 14:28Z].
In run 7a validator-09 lost about 737 samples every 15 s, 102,244 of 658,244 (15.5 %); restarting its agent did not help, and validator-08 lost a batch three times at start-up and then never [O 12:40Z].
Bench 6's run 3 lost a validator's vote-stage series the same way [O 14:28Z].
On every node the per-network counters (`tn_network_*`) collapse into one series, so no per-network figure can be read from Prometheus in either run [RF 7a] [RF 7b].

The agent's config is tn-node-deployment's; it was not edited, and the defect is to be reported to that repository's owners [O 14:28Z].

What stands in is `tasks/bench7/orch-endpoint-sampler.sh`, built at the lost attempt's idle check: one read-only ssh per node per round, a `curl` of the node's own exporter, the text gzipped [O 16:10Z].
It samples all 11 nodes, not only those the idle check named, because a series registered during the blast can move a node's batch boundary [O 16:10Z].
In run 7b it took one sample of all 11 nodes at 17:46:24Z, then one every 60 s from 17:46:32Z to 19:19:36Z: 94 rounds, about 5,100 series a node [RF 7b].
88 rounds hold all 11 nodes and five, during validator-05's outage (18:44:37Z to 18:48:36Z), lack it; the orchestrator's count leaves one round unchecked [O 19:28Z].
The samples are cumulative since the process started, so two samples' difference is the window's total, and the node's own `network` label is intact in them [RF 7b].
Run 7a has no per-minute samples, only end-of-run snapshots of validator-09 and validator-08, which give validator-09's whole-run totals and no time series [RF 7a].
The samples are private and not in the archive [RF 7b].

Where the export and the samples both hold a figure in run 7b, three analyses compared them:
- The engine analysis, samples over export on the validators the export holds whole: over blast 2's mixed phase, executed tx/s 0.9921 to 1.0001, busy ms per s 0.9987 to 1.0003, persist mean 0.9988 to 1.0023 (seven validators) [7b A5 endpoint.cross_check_endpoint_over_prometheus.2]; in its 300-s buckets the worst ratios reach 0.9488 (executed tx/s, bucket 0) and 0.9507 (EVM mean, bucket 3) [7b A5 endpoint.cross_check_endpoint_over_prometheus.2.b0, .2.b3]; the queued-outputs mean, a gauge's average, does not agree (0.0000 to 2.0875 in blast 0) [7b A5 endpoint.cross_check_endpoint_over_prometheus.0].

### What the analysis found about its own tools

A counter the node registers at its first increment has no sample before it, so a window's increase in Prometheus misses each process's first value [C Q6.12].
The loss analysis tested this on the orphan re-pool counter: counted from zero per process, the export equals the log on 10 of 10 validators in run 7b [7b A7 orphans.<node>.counter_check].
The window increase alone reads 48,890 re-pooled transactions against the log's 71,679 in run 7b [C Q6.12], and 25,703 against 42,496 in run 7a, where validator-05's two processes leave part of the gap unexplained [C Q6.11].
The dropped uncertified-batch reports show the same: the export is one report short per node on five nodes in run 7a and on two in run 7b [C Q6.13] [C Q6.14].
A series can stop mid-run: on validator-08 at 18:29:45Z and on the observer at 18:58:45Z in run 7b; the export's check asks only for any sample in the window, so it passed these and validator-05's gap [RF 7b].
The arms summary's prefilter path was not used: on all four runs it filtered the whole logs with the current pattern list, so the four summaries come from one tool and one pattern list, and blocks a bench 6 build cannot fill are absent, not zero [D 32].
The arms summary has no blast-1 row when no second of the blast has all ten generators in their mixed phase; in run 7a generator 06's preamble wait ran its full 600 s, so its summary has two rows, blast 0 and blast 2 cut at the kill [RF 7a] [D 5].
Run 7b's summary has three rows: its generators overlapped in blast 1's mixed phase for 346 s [RF 7b].
A start-up sample of the mode gauge can read `cvv_active` before the node sets its mode, so the rejoin mark was corrected to the first `cvv_active` = 1 after a 0 that follows the start [D 21].
Run 7a's mark (14:16:23Z) agreed with its log line (14:16:03.711Z) to 20 s and was not re-made [RF 7a] [D 21]; run 7b's is 19:12:45Z against the log's 19:12:33.513Z [7b A2 ckpt].
The units' definitions that had to be aligned are listed in §7 under "Definitions that differ".
