- Questions specific to this topic:
  1. **Can the hold stall a proposer?** A held lane is released when its blocker is proven an ancestor, committed, cancelled and re-queued, or forgotten. Is there any reachable state in which a lane stays held forever (a blocker that never leaves the tracked set; a re-send or a restart re-propose that re-creates a blocker; a stale re-send; an epoch boundary), or in which EVERY lane is held so a validator proposes empty headers indefinitely? What bounds the time a digest waits, and does a held digest still count against the worker's admission quota (#1794) so that the hold can back up into the RPC?
  2. **Can a Byzantine committee member make an honest proposer hold?** The blockers are the proposer's OWN tracked headers; the proof of ancestry comes from the parents it chose. Can peers, by withholding votes or by which certificates they deliver, keep an honest validator's lanes held and so censor or delay its transactions more than they can on main (where they can already withhold votes)? Quantify against main.
  3. **Header validity and determinism.** Confirm that no validator checks which digests a header carries or omits beyond main's rules, that the hold changes nothing another node validates, that a mixed fleet (some on, some off) is one chain, and that the plan is a function of the proposer's own state (no time, no hashing order: `BTreeMap`/`BTreeSet` only).
  4. **Does the real drain equal the model's?** The model test's `ProposerModel::drain` with the hold on is the specification; compare it with `drain_digests_for_header` and the record's placement (the model plans and records at drain time in one step: if the proposer records later, what covers the window?).
  5. **Switch off = main, byte for byte** in header contents: the golden test, and a read of every branch the wiring added. Name everything that newly RUNS with the switch off (the bookkeeping maps, counters, log fields) and its memory bound.
  6. **Restart and epoch boundary**: what the hold keeps in memory, what a restart loses (the tracked set, the order record), whether a restart re-propose can execute a digest twice or out of order with the hold on, and what the orphan re-pool does with digests that were held at the epoch's end (HD-3's counters must account for them).
  7. **The hook** (`TN_TEST_OWN_CERT_DELAY_*`): compiled out of a node-scoped release build; with the variables unset in a test-utils build it changes nothing; when set it only delays this node's own certificate (it never signs, stores or sends anything it otherwise would not).
  8. **Unbounded growth**: the per-lane sequence maps, the order record and the tracked set under a validator that is never certified for a long time (a far validator at full load: the benchmark's case).
  9. **The open design question (the wiring unit's F1): which digests trigger a header.** The run loop builds a header before the minimum delay when the queue holds at least `header_num_of_batches_threshold` digests. Held digests stay in the queue and are counted, so a held backlog makes the proposer skip the minimum delay for a header that can carry none of them. As built: under load the trigger fires as on main (the queue is above the threshold either way) and only the payload differs; at light load a held backlog makes headers come earlier than main's would, which gives the own certificate less time to arrive and may create more blockers (self-feeding on a far validator). The alternative offered: with the switch on, count only digests outside held lanes (about 15 lines; then a validator whose only lane is held proposes at the minimum-delay cadence, slower than main under load: on the benchmark fleet every validator has ONE worker, so one held lane is its whole queue). A third reading: count what main would count (digests that arrived since the last header). For each of the three: liveness and round cadence of a far validator at load and at light load, effect on other validators (its header as a parent, leader rounds), whether it can be driven by a Byzantine minority, and whether it keeps the design's statement "header contents only, no timing change". Recommend one, with what a fleet run must measure to confirm it. This is the question the user decides: be exact about what is known from code and what is inference.
