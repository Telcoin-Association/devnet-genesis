The headline is a 40-minute mean: run 2's rate fell through the blast from 6,092 tx/s in the first five minutes to 4,719 in the last full five, while run 2b's held at 7,077-7,684 (`A1/kpis.md` "The load blast over 40 minutes").

Findings, ranked by what they change for the upstream fixes and the next run (§4 has the detail):

1. The disk's write-rate limit bounds the fleet at full load.
   In run 1 every warm full-load minute sat at 19,900-20,100 device writes per second per validator, the provisioned 20,000 IOPS, so the executed rate is 20,000 over the writes per transaction (run 1 `A4p/cache.md` §3).
   Writes per transaction follow output size, database size and key density, and no switch moves them by more than about 7 % by itself (run 1 `A8/writes-model.md`).
   Run 2 sat at 0.998 of the limit for 40 minutes and its rate fell 15 % from minutes 1-4 to 35-39 as writes per transaction rose with the database; run 2b's device ran at half its limit and the rate held (`A4p/disk.md`, `A4p/model-check.md`).
   Solid: measured in all three runs from two sources (node counters and Cloud Monitoring); the model of writes per transaction is a fit, not a mechanism.
2. Bench 5's write amplification is understood and gone.
   It is the state of a node's first process after genesis, in which libmdbx skips its prefault writes and new pages land in large folios that are written back whole (run 1 `I-9/findings.md`).
   Run 1's validators escaped it only because the control arm restarted them against the plan; the observer, not restarted, wrote 6.5-10.9 times its page bytes.
   With `mdbx_random_advice` on from the first start, every node of runs 2 and 2b, the observer included, wrote single pages from genesis to the end at 1.06-1.19 times the page bytes (`A4p/disk.md` §4).
   Solid: the state and the restart that ends it are measured step by step on run 1's eleven nodes; what starts it is a correlation; whether bench 5's nodes blasted in their first process was not checked.
3. The vote fix holds while the disk binds and lost certification when it did not.
   Run 2 certified 99.1 % or more on every validator in every window with no refused-behind vote under load (`A2/certification.md`).
   In run 2b four validators lost certification over blast 2 (v06 44.5 %), because the always-on form names its author's tip minus 8 outputs and, with the disk off its limit, the engines' execution spread to 18-45 outputs (`I-10/findings.md`).
   On the same measured tips a floor of 32 outputs would have kept every validator at 99.7 % or more; that is arithmetic with rounds held fixed, not a result.
   It is a liveness and throughput problem of the proposers, not a safety one: no fork or halt line in either run.
   Solid: per-header join measured on run 2b; the round-trip step is inferred because vote arrival is not logged.
4. Every epoch record of all three runs certified on one hash and one closing block, and the margin was once at its minimum.
   The 31 closes of runs 1 and 2 (`E-1/findings.md`) and the six of run 2b (`A3a/closes.md`) agree on every node; run 2b's close inside the outage certified with exactly 7 voters.
   The vote fix does not reach the record path, and no test crosses a close with the always-on form (`E-2/findings.md`).
   The error line `failed to reach quorum on epoch close` fired 11 times, each time on a record the network had certified.
   Solid: measured and read from code; the signer count is a collecting node's view, since no log names the signer set.
5. The 16-minute follower stretch after a kill is the rejoin rule working under load.
   The follower replays at its own execution rate, below the fleet's output rate under load (1.33 against 1.41 outputs/s in run 2), so its deficit grew until the load ended (`A3a/recovery.md`).
   While it followed, its RPC refused every transaction: generator 05 landed nothing for the last 949 s (run 2) and 899 s (run 2b) of the blast, and v05 missed signing the next record.
   Solid: measured and read from code; that it would never rejoin under a load that does not stop is inferred from the trend.
6. At 50,000 IOPS the engine's sequential cycle sets the ceiling.
   Execute and persist run in series; the costliest engine (v01, 136.9 µs/tx) has a capacity of 7,287 tx/s, which is the fleet's executed rate, and the persist is a third of its cycle (`A4e/engine.md`).
   Run 1's 8,600-10,300 tx/s extrapolation left the persist out.
   Solid: measured; what held the input at v01's capacity was not measured.
7. Run 1 settled what each switch does, well enough to choose the configuration (§4.7).
   `sealed_tx_keep` alone causes the pool group's side effects (run 1 `I-7/findings.md`), and nothing in the node sizes a consensus output (run 1 `I-8/findings.md`).
   Solid: most effects measured, several confounded with cache state or output size.
8. The floor did not move (1.50 s seen p50 by stage in every run and in bench 5), and under load the consensus part of the land path halved while the engine queue grew, so seen p50 at 600 × 16 barely moved (`A6/stages.md` §4).
   Solid: measured; the stage tool's sum is within 250 ms of seen on 99.4 % of run 2's load blocks.
9. The census found no hard-check line; warn and error lines rose against run 1, mostly from the outage and the follower (`A3b/census.md`).
   Solid for the node's main log on 11 of 11 nodes; its stderr file was not pulled.

What stays open (§6): the floor of the vote fix under an execution spread; rejoin under sustained load and the follower's dead RPC; the epoch-record margin and its untested paths; pipelined persist at 50,000 IOPS and group commit at 20,000; `sealed_tx_keep`'s side effects; the far validators without the parent grace.
After the rulings on the open verdicts (`A7/orchestrator-rulings.md`), run 2 met 15 of its 22 acceptance lines and failed 2, both named to the user in advance; run 2b met 14 and failed 2, one of them (certification) unexpected (§3).

### 4.1 The disk's write-rate limit bounds the fleet at full load

Measured.
- Run 1: every warm 600 × 16 minute ran at 19,900-20,100 device writes per second per validator in writes of 4.6-5.3 KiB (run 1 `A4p/cache.md` §3); Cloud Monitoring puts each validator's ten highest minutes at 19,976-20,344 (run 1 `cross-unit-notes.md`).
  The opening control made 3.09 writes per transaction and executed 6,155 tx/s; the closing control, on a database 4.1 times larger with outputs 23 % smaller, made 5.06 and landed 2,852 (run 1 `A7/verdicts.md` §0, §8).
  The cold cache after an eviction explains 7-27 % of that fall; the rest is writes per transaction at the limit (run 1 `A4p/cache.md`).
- Run 2: 19,967 [19,946-19,984] writes per second over blast 2 (0.998 of 20,000), 5.0 KiB each, 109 flushes per second, 2 msyncs per output, 3.74 writes per executed transaction, commit 75 µs/tx (276-294 ms per output) (`A4p/disk.md` §1, "Answer").
  The executed rate fell from 6,701 tx/s in minute 0 to 4,508-4,846 in minutes 35-39 while writes per transaction rose from 2.94 to 4.1-4.5; every engine was 981-999 ms/s busy with its queue at the cap of 8 in 95-100 % of samples (`A4e/engine.md` "Answer").
- Run 2b: 24,837 writes per second (0.497 of 50,000), 5.1 KiB each, 3.41 writes per transaction, commit 22 µs/tx, 123 MiB/s mean against 800 (busiest second 260 MiB/s), device busy 0.17 of the time against 0.39 in run 2; the rate held (`A4p/disk.md` "Answer").

Mechanism.
- The pages a commit copies are a property of the output and the database, not of the node: all ten validators copied the same pages for each of 8,828 outputs, at fault rates from 7 to 876 per second (run 1 `A8/writes-model.md` "Answer", measured).
- Across run 1's blasts copied pages per transaction go as output size^−0.375 × database size^+0.224, and a third variable, distinct accounts per transaction (key density), adds about 22 % at 0.65-0.80 against 0.44-0.46 (a fit).
  A page-touch count of each output's keys against each table's pages, with one fitted factor, reproduces every blast within −6 % to +14 %, which is why output size and database size act together (run 1 `A8/writes-model.md` §2.4).
- Device writes per page held at 0.90-1.00 in both runs; the page-touch count missed run 2's and run 2b's pages by 0.5 % and 1.0 %, while the power-law fit over-predicted by 9.1 % and 7.0 % and, refitted inside one blast, gives exponents of −0.33 on output size and +0.05 to +0.10 on database size (`A4p/model-check.md` "Answer", §3).
  Inside a blast the database is collinear with time, so that refit is a fit, not a mechanism.
- Output size is the executed rate times the commit interval (two rounds); nothing in the node sizes it, the proposer fires on its 350 ms minimum delay, and through the closed generator loop any change in page cost moves output size and rate 1.6 times (run 1 `I-8/findings.md` "Answer", read and measured).
  The identity held within 0.6 % in runs 2 and 2b (`A4e/engine.md` "Answer").

Against run 1's prediction: run 2's 40-minute mean (5,328 tx/s, nine validators) is inside the model's 5,150-5,650; the fall was shallower, 15 % from minutes 1-4 to 35-39 against 18-19 % for the fixed-output arithmetic and 27 % for the fit fed the measured outputs (`A4p/model-check.md` §4).
Against run 1's always-form arm at the same limit, run 2 made 3.74 writes per transaction against 5.06, which gives 5,348 and 3,953 tx/s at 20,000 (arithmetic) against 5,328 and 3,954 executed; whether output size (3,898 against 2,901), database size or cache state carried the difference is not separated (`A7/comparison.md` §3).

For the upstream fixes: on this disk a throughput claim is a claim about writes per transaction, and "5,322 against bench 5's 3,449" compares a run bound by write count with one bound by bytes (G3 brief §1).
The levers are larger outputs per commit: run 1's arithmetic gives 1.29, 1.66 and 2.14 times the rate for 2, 4 and 8 outputs per commit at 1.5 GiB (only 2 inside the measured sizes), and 1.17 times for a commit interval 29 % longer (model, about ±11 %) (run 1 `I-8/findings.md` §5).
None has run.

### 4.2 Bench 5's write amplification: a first process that skips its prefaults

Measured in run 1 (run 1 `I-9/findings.md`).
- Every one of the eleven nodes entered the same state in its first process after genesis: from output 9 (15:49:22) pages ahead of the allocation frontier were already in the page cache, libmdbx skipped its prefault writes (125 prefaulted of 677 grown pages, identical on all eleven), and new pages landed in order-4 and order-5 folios.
- The control arm's apply restarted the ten validators at 16:01:52-16:05:25, because the arm tool could not read their running switches (R1-D4), and left the observer running.
  The restart's open discards the file past its used size, which removed the read-ahead pages; 98 later processes on all eleven nodes prefaulted 1.00-1.52 times their growth.
- The observer kept its first process through the control's three blasts (prefault 0.29 of growth) and wrote 6.5-10.9 times its page bytes in 154-230 KiB writes (run 1 `A4p/persist.md` §2); after `p1`'s eviction and restart it wrote 1.06 times.

Mechanism: measured at each step (the state lived in the first process, the tail removal ended it, resident frontier pages make libmdbx skip prefaults, skipped pages in large folios were written whole); that a multi-page prefault at outputs 9-11 started it is a correlation, since the node logs no per-allocation detail.
So run 1's verdict "`mdbx_random_advice`: nothing measurable on the validators" holds only because the validators had already left the state by accident.

Runs 2 and 2b, with the advice on before the first start (`A4p/disk.md` §4):
- Single-page writes from genesis to the end on every node, the observer included, through v05's restart and the observer's.
- Every process prefaulted 1.000-1.025 times the file's growth in every blast; before blast 0, 19-24 outputs per node made the multi-page prefault writes that opened run 1's window, and the prefaults still covered the growth (2,232 pages for 2,199 grown in run 2, 2,256 for 2,223 in run 2b).
- No folio above order 3; `thp_file_alloc` 0; the advised range equal to the whole mapping on every line.
- At full load 1.156-1.193 device bytes per page byte on validators and 1.06 on the observer, in 5.0 KiB writes; bench 5 wrote 10-13 times in 227 KB writes, about 2,400 per second, 0.68 per transaction, at the 800 MiB/s byte limit during each commit (run 1 `A8/writes-model.md` §4, through the model).
- One loose end: resident pages past the used size rose above 30 in isolated five-minute samples of ten node processes and were back to 0-32 five minutes later, with prefault at 1.000 across them; the files cannot show whether those samples caught a commit in flight.

How solid: high for runs 1, 2 and 2b.
That bench 5's amplification was this state is the explanation that fits its signature on every node; whether bench 5's nodes blasted in their first process after genesis was not checked (run 1 `I-9/findings.md` "What remains unknown").
For the upstream fixes: the advice from the first process (or a restart after genesis before load) is what keeps a fresh deployment out of bench 5's state.

### 4.3 The vote fix: confirmed while the disk binds, lost certification at 50,000 IOPS

Measured.
- Run 1, at 600 × 16 mixed: the adaptive form lifted the worst three validators from 93-95 % to 98.5-98.7 % and cut refused-behind votes from 2,398 to 126; the always-on form gave 99.9 % and 0, but 84.6 % in its warm-up against the adaptive form's 96.3 %, at different cache states (run 1 `A7/verdicts.md` "The twelve switches").
  Without the fix (`a0-prime`) v08-v10 certified 27-72 %.
- Run 2: every validator at 99.1 % or more in every window, 99.7 % or more over blast 2's mixed phase; 0 refused-behind votes and 0 vote timeouts in blast 2 (86 `superseded` answers); `lock_ms` p95 0 on every voter; execution lag even at 35-45 rounds on every node (`A2/certification.md`).
  Bench 5 had certified 0.0-16.3 % on its three fastest validators before the kill, with 47,614 refused votes (`A7/comparison.md` §1).
- Run 2b: as good through both light blasts, the warm-up and blast 2's first 120 s; then over the mixed phase v06 44.5 %, v10 68.2 %, v02 78.6 %, v09 95.8 % (v06's lowest bucket 18.7 %), the other six 99.9-100 %.
  Before the kill v05 answered `superseded` to 33,414 vote requests and cast 2,908 votes, v01 20,507 and 16,153; the fleet logged 265 refused-behind votes and 93,730 `superseded` answers, and the median round slowed from 353 to 374 ms (`A2/certification.md`).

Mechanism (`I-10/findings.md` "The answer", §1-§3).
1. The always-on form names its author's own tip minus 8 executed outputs on 97-99 % of headers: its inputs are the parents' earlier picks and the floor is the only way up (read and measured).
2. In run 2b v06 ran about 18 outputs ahead of v01 and 45 ahead of v05, and 7-9 ahead of v04 and v02, so the block a fast author named was one that four or five voters had not executed (measured; rounds to outputs inferred at two rounds per output).
3. A voter without the block waits up to 1 s before the lock; the author's next header comes about 360 ms later, so the voter answers `superseded`, and neither that nor `behind` is a vote (read and measured).
4. With four voters out a header cannot certify (0 of v06's 1,643 headers with five or fewer timely votes); with exactly six it certified only when the six round trips fit inside the round: 99 % for v09 in Seoul, whose six are near, 39 % for v06 and 48 % for v10 (measured; the round-trip step inferred, because vote arrival is not logged).
5. The spread came from the engines: with the disk off its limit each engine ran at its own cost (130.6-136.9 µs/tx), the input settled at the costliest engines' capacity, v01, v04 and v05 kept full queues while v06 drained to about one output, and v05 and v01 fell steadily behind (measured; the queueing step read).
   In run 2 the disk gave every engine the same cost, 187.0-187.3 µs/tx, so its pass holds only while the disk binds.

Each form of the rule recomputed on run 2b's measured tips before the kill, with rounds and leaders held fixed (`I-10/findings.md` §4; arithmetic, not a simulation):

Safety (`I-10/findings.md` §5, read): a vote is signed only after the voter finds the named number and hash in its own chain, and the subscriber checks each committed leader's block the same way; no node logged `unexpected execution result`, `execution has forked`, `we have forked` or a halt line in either run (`A3b/census.md`).

### 4.4 Epoch records: one state at every close, thin margins, untested paths

Measured.
- All 31 closes of runs 1 and 2, and the six of run 2b, certified with at least 7 of 10 validators; every vote, quorum line, fetched record and recovered certificate carried one record hash per epoch, and every node one closing block (`E-1/findings.md` "The answer"; `A3a/closes.md`).
  No node logged a fork, a vote for another hash, a state-check halt or a skipped state check.
  The state check ran on late validators and passed; it never had a mismatch to catch.
- A stored certificate undercounts the voters, because a collector drops votes that arrive before it has built its own record; validators that had voted before the first quorum line are the better margin (`E-1/findings.md` "How close to the edge"):

| run, close | signers (min over nodes) | voted before the first quorum line | 7th to 8th vote, s | commit gap, s |
|---|---:|---|---:|---:|
| run 1, 20:00:32 (adaptive) | 7 | 7 | 4.17 | n/a |
| run 2, 15:01:58 (blast 1) | 7 | 8 | 1.32 | 3.48 |
| run 2, 15:21:58 | 7 | 9 | 0.45 | 14.49 |

| run 2b, 17:42:19 (blast 1) | 7 | 8 | 0.51 | 3.42 |

| run 2b, 18:22:19 (outage) | 7 | 7 of the 9 running | no eighth vote | 10.31 |

Sources: `E-1/findings.md`; `A3a/closes.md` "How close to the edge", "Run 2 against run 2b"; `A7/comparison.md` §2.
Run 2b's outage close is the thinnest of the program: v05 was down and v01 and v02 were still draining 15-output backlogs when the seventh vote went out at 11.30 s.
The late validator was v05 in run 2 (v01 and v04 at 15:01:58) and v01 at every loaded close of run 2b; bench 5's two loaded closes had exactly 7 signers with commit gaps of 22.5 and 11.0 s.
In run 2b, 19 minutes before its kill, v05 was demoted twice at the 18:02:19 close for 4.05 s in all (`reason=epoch_behind`), with one failed promotion (`A3a/recovery.md`).

Read from code (`E-1/findings.md`, `E-2/findings.md` "The answer").
- A validator builds its record only after its own engine has executed the closing output; `final_state` is its own latest executed block, the digest covers it, and a collector counts only votes for its own hash.
  `quorum_exec_block` changes only the block a header names, and nothing in the record path reads it.
- Safety holds with at most f faulty members: a certificate means at least 7 members, 4 of them honest, executed the closing block to the same hash, with the fix off, adaptive or always on.
- Liveness holds under a condition the fix does not create: the record certifies in its first round only if 7 members finish the closing output within the earliest collectors' window (25 timed-out 2.5-s waits, about 62.5 s); otherwise the next close re-votes it, and the chain does not wait.
  Neither form bounds the fastest or the slowest f members.
- Detection is up to 8 non-empty outputs later with the fix; a divergence in an epoch's last outputs shows at the record or at the next epoch's first leader.

Not covered by any test (`E-2/findings.md` §4): a close with the always-on form; a member past the 8-output floor or killed through a close, and its adoption of the stored record end to end; a failed record round re-voted at the next close; the state check firing end to end on a diverged closing block; detection timing with the fix; the first headers of a new epoch under the quorum rule in a running fleet; votes across members whose previous records differ.

The false alarm: `failed to reach quorum on epoch close` (error level) fired 11 times over the three runs (9 on validators at 6 closes and 1 on the observer in runs 1 and 2, 1 in run 2b on v04 72.79 s after the 18:02:19 close), each time on a record the network had certified (`A3a/closes.md` "reconciled").
Once a record is certified the gossip handler drops further votes, so the node's own round stays at the 1-5 votes it had and times out after 25 waits, then fetches the same hash from a peer (`E-1/findings.md`, read and measured).

For the upstream fixes: the record path is sound as read and as measured, and the margin follows how unevenly execution stands at the close; the always-on form needs the close tests above, a counter on the state check's result, and an end to the false error, before it ships.

### 4.5 Recovery after a kill: the rejoin rule under load

Measured (`A3a/recovery.md` "The answer").
- Kill to `CvvActive` 21m40.7s (run 2) and 21m30.2s (run 2b), against bench 5's 28m05.8s; start to `CvvActive` 16m40.8s and 16m30.1s, against 23m05.7s.
  One promotion per kill, held; no failed promotion; the attempt cap never reached; first certified header 0.8-0.9 s after the promotion.
- Three stretches: replay of the already-closed epoch 4 (2m04s and 3m02s, including 41.3 s and 48.8 s with no output delivered while state sync filled its cache); epoch 5 under load, entered 452 and 470 outputs behind, replayed at 1.332 outputs/s against the fleet's 1.409 (run 2) and 1.180 against 1.243 (run 2b), so the deficit grew to 527 and 585; then the post-load outputs, epoch 5's close and promotion at the start of epoch 6.
- While it followed, v05's RPC refused every transaction (§3), it refused 20,402 and 17,586 votes as inactive (`A2/certification.md`), it logged 21,157 (run 2) and 7,604 plus about 9,300 (run 2b) certificate refusals, and it reached epoch 5's close 40.8 s and 28.8 s after the record certified, so it signed neither record after its kill.
- The observer followed the chain again 23.3 s (run 2) and 8.0 s (run 2b) after its restart command.

Mechanism (read from code): a follower may promote only from an output of its open epoch within 20 rounds (`rejoin_window`) of the newest known header, and state sync hands it an output only after its own execution reached the block that output's leader names, so it replays no faster than it executes.
Under a load that holds the committee at its execution limit, a follower on the same machine cannot close a deficit (measured here; inferred as a rule).
Bench 5's follower gained 7 outputs a minute only because refused votes held its network below its execution rate; the vote fix removed that slack.
That it would never rejoin under a load that does not stop is an inference from the trend (4-8 outputs a minute).

For the upstream fixes: the rejoin code does what it says; the 16-minute stretch comes from its premise.
The levers are a rejoin that does not wait for a full replay (from a snapshot of the committee's executed head, or promotion with execution allowed to lag inside the activity window; neither exists at 2df831e3c) and a follower RPC that forwards transactions, or a generator that takes the error's advice and fails over.

### 4.6 At 50,000 IOPS the engine's sequential cycle sets the ceiling

Measured (`A4e/engine.md`).
- The cycle is sequential in both runs: no `output executed` line carries a `pipelined` field, no task started before the previous ended, and `tn_engine_commit_interval_seconds` counted 0.
- Per executed transaction over blast 2, nine validators pooled: run 2 187.2 µs = execute 90.2 + persist 95.2 (save 20.9, commit 74.2) + announce 0.7; run 2b 133.9 µs = execute 87.7 + persist 44.5 (save 21.9, commit 22.4) + announce 0.75.
  From run 2 to run 2b the task fell 53.3 µs/tx, 51.8 of it in the commit; the rate rose 37 % and the seconds per output 9.6 % (committed rounds per second 2.76 in run 2, 2.52 in run 2b), so outputs grew 50 %.
- Run 2b's fleet ran at 975 ms/s busy with its queue at the cap in 42 % of samples (3-98 % by validator).

## 6. Open questions and what a next run could test

Ranked by what an answer would change for the upstream fixes or the next run, the first most; the options are not decisions (`A7/open-questions.md`, with run 1 `A7/candidates.md` where noted).

1. The vote fix's floor under an execution spread.
   It decides the shape of the proposer-side fix before it goes upstream, and every faster configuration widens the spread (§4.3).
   Missing: when a vote reaches its author (not logged); the replay holds rounds fixed; the same per-header join on run 2 and on run 1's always arm; what held run 2b's input at v01's capacity.
   Options: deepen the floor to 16 or 32 outputs (the ring holds 50 entries); a quorum over fresh tips with a margin, a wire change behind a fork gate; measure vote arrival first; couple admission to the backlog (`rpc_admission_backlog_outputs`, whose costs run 1 measured).
2. Rejoin under sustained load.
   The follower stretch is the largest user-visible loss in both runs (§4.5).
   Missing: a run whose load continues past the expected rejoin, to measure the trend rather than infer it; what state sync does in the 41-49 s before the first replayed output.
   Options: a rejoin that does not wait for a full replay; a follower RPC that forwards transactions, or a generator that fails over; a chaos variant with the load continuing.
3. The epoch-record margin and its untested paths.
   No record failed, but the always-on form ships with no test that crosses a close, and the margin was at its minimum once (§4.4).
   Options: the e2e tests E-2 lists (two closes with the always-on form and one member slowed past the floor; a hook that alters one node's closing block; a missed window re-voted); a counter on the state check's result and a field naming the last vote's arrival on `epoch record quorum`; end or downgrade the false quorum error once a certificate for the same hash is held.
4. Pipelined persist where the disk does not bind.
   The largest throughput lever left at 50,000 IOPS (11,397 tx/s with the persist free, arithmetic), untested there; its effect on the spread of question 1 is unknown (§4.6).
   Options: an arm at 50,000 IOPS with pipelined persist beside a deeper floor, so the certification loss does not mask the throughput; or take run 2b's 7,300 tx/s as this configuration's figure at that disk.
5. Group commit and the commit cadence.
   On the 20,000-IOPS disk the rate is the limit over writes per transaction, so output size is the lever; run 2's engine queue sat at its cap 99 % of the time, so two to four outputs already wait when one finishes (§4.1).
   Missing: neither option has run, and merging outputs changes what "8 outputs back" means in seconds.
   Options: merge queued outputs before the persist (engine only); grow the proposer's minimum delay with the backlog, or raise `min_header_delay` as a fixed setting.
6. `sealed_tx_keep`'s side effects.
   The pool and visibility lines failed in both runs with the switches off (30,497 and 120,778 gap-resend landings at or past 300 s; 183 and 14,928 unlanded), and the keep brings measured costs (§4.7).
   Missing: transactions per sender per output with the keep on and off; whether run 2b's unlanded transactions are bench 5's sealed-but-uncommitted gap.
   Options: hold back a sender's later nonces after a skip; keep re-queued digests from being overtaken (run 1's grace arm had zero re-queues); refuse an identical rebuild in the builder.
7. The far validators without the grace.
   Generators 02 and 06 land 9-12 % of the others' rate at light load in every run; v06 and v02 were also among the four authors that lost certification in run 2b.
   Missing: the grace with the always-on form under load (run 1's `gr150` ran with the adaptive form, the bound and the pipeline); why v10 lost its leader rounds under the grace (run 1 `A7/candidates.md` §10).
   Options: an arm with the grace on top of run 2's configuration at 20,000 and 50,000 IOPS; a grace shorter than 150 ms.
8. Smaller leads from run 1 (`A7/candidates.md`): every stop ends `All tasks NOT shutdown` after 2.0 s (§12); one validator lags at every loaded close (v02 in run 1, v05 and then v01 in runs 2 and 2b), unexplained (§4; `A3a/closes.md` "Not known"); blast 1's execute cost above blast 2's (`A4e/engine.md`); run 2's floor seen p95 of 2.27 s (`A6/stages.md` §4a).

### 8.4 Findings, ranked by what they change for the choice of form

#### 8.4.1 The forms are the same on throughput, engine, disk, closes and recovery

Measured on both disks (§8.3): blast 2 and blast 1 chain tx/s, the engine's task cost per transaction, the device's share of its limit, the closes and validator-05's rejoin all sit inside the always-on twin's spread; no node in any of the four runs logged a halt, fork, unexpected execution result, fatal database text or panic.
At 20,000 IOPS both forms ran the device at its write limit with the engines busy 994-996 ms/s; r3-A4p calls that disk-bound and r3-A4e engine-bound with the device at its limit, the same measurements under two labels (comparison §8 item 6). At 50,000 IOPS the engine bound both forms.
The one exception is run 3's floor blast, 684.7 tx/s, 9.5 tx/s under run 2's lowest block: generators 02 and 06 landed 3 % of the other eight's median against 11-12 %, with 0 resends and 0 skips, which agrees with their start 59-89 s late against 23-48 s [measured; the cause is not in the engine data].
At matched output size run 3b's engine is 0.4-1.8 µs/tx dearer from 3,000 transactions per output up; cause not measured, and r3-A4e names the 46-minute longer chain as an untested candidate.
What it changes: the choice of form rests on own-header certification and the senders' cost.

#### 8.4.2 At 50,000 IOPS neither form holds certification, and the adaptive run certified more on the same block

Measured: over B2 mixed run 3b certified 94.82 % of own headers (2,807 lost of 54,226) against 88.26 % (7,025 of 59,826); validator-06 84.1 % against 44.5 %.
Inside the starved windows the adaptive form named a block 7.94-7.97 outputs behind the author's tip, the always-on floor; six or seven proposers were windowed for 996 of the 1,029 pre-kill seconds, 92 % of the pre-kill losses sit inside windows on floor-8 headers, and the floor-8 rule on run 3b's tips predicts 93.2 % against 92.8 % measured [arithmetic].
The three slowest members (01, 04, 05) named their own tip on 99.9-100 % of their headers and certified 100 %; under the always-on form the same three certified 99.9-100 % at the floor.
The gain sits on headers past the floor: with a lead over the 7th member of 9 outputs or more, 75.4 against 22.7 % certified (B2 mixed), and at the same lead run 3b's headers lived longer before the author's next header [measured].
Rounds with 4 or more under-held headers were 17.1 against 0.46 % of rounds, and 76.5-81.3 against 8.9-32.7 % of those headers certified [measured association]; a round's next header needs 7 parent certificates (quorum threshold 7 of 10, `crates/types/src/committee.rs:1191-1193`; parents forwarded only at that weight, `crates/consensus/primary/src/aggregators/certificates.rs:92`; required before the next header, `crates/consensus/primary/src/proposer.rs:772-775`) [read from code by the orchestrator; r3-R had it as inferred]; that this wait is why run 3b certified more is r3-R's reading.
Alongside those rounds, run 3b's round rate was 6.8 % lower before the kill (a tail: p50 +4 ms, p99 +497 ms) and outputs 6-8 % larger; output size accounts for 1.4-1.8 of the 5.77-point pre-kill gap [inferred: arithmetic].
The adaptive form also lowered three validators that held under the always-on form: before the kill validators 08, 03 and 07 at 95.9, 98.5 and 98.5 % against 100 %, outside run 2b's bucket ranges; and seven validators sat under 99 % in blast 2's first 120 s against none.
Not separated: which validators lagged differs between the runs (validator-04 and then validator-02 in run 3b, validator-01 in run 2b), and r3-R could not tell that from the form.
The units disagree on the noise: the 6.4-point gap of bucket means is inside run 2b's 10.6-point bucket range (r3-A2) and outside the spread of its two windows, 87.0 and 87.3 % (r3-I10); r3-R's pre-kill buckets are 77.3-93.2 against 91.5-94.4 %.
They also disagree on why run 2b's fast members led by 10 or more outputs more often: r3-I10 infers each node's engine rate and backlog; r3-R measured the authors' engines at 7,400-7,460 tx/s across the lead span in both runs and puts it in the fleet's spread and the under-held rounds (comparison §8 items 2 and 5).
What it changes: at this disk the adaptive form does not remove §4.3's floor problem, since its fast proposers named what the always-on form names; whether its higher certification belongs to the form or to this run's fleet is not settled by one run per form.

#### 8.4.3 The senders pay more under the adaptive form on both disks, through the same reordering

Measured (§8.3, last table): 3.54 and 1.96 times the gap resends with generator 05 left out, 4.03 and 1.91 times the `nonce_too_high` skips, 59 and 1.4 times the unlanded transactions (ratios as r3-L gives them, 20,000 and 50,000 IOPS); the faster disk multiplied the always-on form's resends by 4.4 and the adaptive form's by 2.4.
The mechanism is the same in all four runs: a cancelled or late-committed own header's batches are re-queued behind batches a newer own header already carried, the sender's later transactions are skipped as `nonce_too_high` and sit in no pool, and the generator resends its window after its 300-s gap check (`proposer.rs:996-999`, `:1004-1071`, `:1090`; issue #1807) [read].
Every gap-resend second of generators 01-04 and 06-10 fell 280-345 s after a lost own header of the generator's own validator: 31 of 31 in run 2, 124 of 124 in run 3, 175 of 177 in run 2b, 385 of 385 in run 3b [measured].
The adaptive form exposed that loss on more validators in more minutes (104 against 23 and 226 against 81 validator-minutes) [measured], though at 50,000 IOPS it lost fewer headers with overtaken own transactions (858 against 2,202); that the breadth sets the totals is r3-L's inference, and a sender's 300-s cycle caps its resends at about 9,600 per 5 minutes [measured ceiling].
At 50,000 IOPS 69 % of the difference comes from validators that barely lost a header under the always-on form, and re-queued batches executed 5.5-14 s after the loss in run 3b against up to 172.5 s in run 2b; at 20,000 IOPS the first resend wave opened from the near validators' cancelled own-tip headers in blast 2's warm-up (22:43:59-22:45:10Z) [measured].
What it changes: on both disks the senders' cost counts against the adaptive form, through a mechanism both forms share, with `sealed_tx_keep` and `digest_dedupe` off in all four runs; one run per cell.

#### 8.4.4 At 20,000 IOPS, and in blast 2's first 120 s on both disks, the adaptive form certifies a little less

Measured: over B2 mixed run 3 certified 99.64 % against 99.94 %; before the kill validators 02, 06 and 10 sat at 98.8-98.9 % against 99.8-100 %, outside run 2's bucket range for each.
Before the kill the adaptive form named the author's own tip on 66.1 % of headers (always-on 0.2 %), 1.21 outputs behind the tip on the mean (about 0.9 s) against 7.59 (about 5.5 s).
Validators 02, 06 and 10 had 95.7-97.4 % of their own headers inside a starved window and entered one 78-83 times an hour; inside they certified 99.81-99.95 %, outside 56.6-77.9 %, and every return to the own tip lost a header, 1.19-1.39 per return [measured]; that a one-output lead fails the tip header within a 353-ms round is inferred.
The round rate was 1.1 % lower before the kill: the certify stage was 14 ms longer (buckets 0.230-0.246 against 0.219-0.225 s, no overlap) as the window's quorum headers certified later (p50 0.287 against 0.171 s) [measured], and `min_delay` absorbed most of it (r3-R).
The slow voters (05, 04, 03) answered `superseded` 3,164 times before the kill against 85, on others' own-tip headers, and 2,747 of 3,148 joined answers fell on headers certified anyway.
In blast 2's first 120 s the adaptive fleet certified 97.98 against 100.0 % (20,000 IOPS) and 98.02 against 99.97 % (50,000 IOPS); no unit joined that window per header; the window state resets at each epoch [measured] and after 64 certified tip headers [read], consistent with every author naming its tip when load begins, and not tested.
The lead never reached the floor at this disk (0.01-0.02 % of headers), and the floor-8 rule on run 3's tips predicts 99.8-100 % per validator [arithmetic].
What it changes: at 20,000 IOPS the adaptive form gives up about 0.3 points of fleet certification, about 1 point on three validators, for a named block about 0.9 s old against 5.5 s; what the fresher block is worth downstream was not measured.

#### 8.4.5 A deeper floor, as arithmetic

On the measured pre-kill tips, with tips and rounds held fixed, a floor of 16 outputs gives 100.0 % on run 3b's tips and 97.0 % on run 2b's, and a floor of 32 gives 100.0 and 99.9 % (I10-3b §5); at 20,000 IOPS floors 8, 16 and 32 all predict 99.8-100 % (I10-3 §6) [arithmetic].
The price is a named block 16 or 32 outputs old on every header that uses the rule, under either form.
No run tested a deeper floor, and a different floor would move the tips and rounds the arithmetic holds fixed.
What it changes: it extends §4.3's table to run 3b's tips; the floor's depth stays an untested option for both forms.

### 8.6 What stays open

The comparison leaves these to the user (its §9):
1. Which cost counts more, own-header certification or the senders' resends and unlanded transactions: at 20,000 IOPS the always-on form is ahead on both; at 50,000 IOPS the adaptive form is ahead on certification and behind on the senders' cost.
2. The floor's depth, so far arithmetic only (§8.4.5).
