## Why
Fleet actions of the benchmark run detached: `benchmark/launch/launch.sh <env> <segment>` starts a segment with `nohup setsid`,
records its pid from inside and writes an rc line when it ends (`benchmark/launch/README.md` is the contract). The `arms`
segment runs `benchmark/launch/run-arms.sh`, which applies an arm and then starts each blast with
`benchmark/benchmark-blast.sh run --yes`; that driver creates load VMs, waits for the blast, collects, and deletes the VMs.
Unit H13 found: on TERM, `launch.sh`'s `on_sig` signals `run-arms.sh` only; `run-arms.sh` has no trap, so it dies, and the
blast driver it started keeps running as an orphan. The segment's rc line (`rc=143`) is written at once, while a blast is still
loading the fleet. An operator who reads "ended" and starts the next action (a resume, a teardown, another arm) then has two
fleet actions running at once on a fleet that costs money and cannot be re-run cheaply. Killing the driver instead would be
worse: its load VMs would be left running and undeleted.

## Deliver
1. **`run-arms.sh` on TERM (and INT): finish what is running, start nothing new, then stop.** While an arm apply or a blast
   driver is running, a signal is remembered and the child is left alone; when the child returns, the walk stops the way a
   blast that failed twice stops (the arm stays open, the stop reason says it was a signal, the resume line is printed), with
   an exit code that tells a signalled stop from a failure. A second signal during the wait changes nothing (say so in the
   log line it prints). Between children (the pool gate's wait, the epoch-boundary wait, a ready wait) the walk stops at once.
   Decide and document what happens to an arm apply that is interrupted halfway — read `benchmark/params-apply.sh`'s own
   signal handling first and do not weaken it.
2. **`launch.sh`: the rc line is written only when the segment's process group has nothing left running.** Whatever the
   segment (read how each of the segments is started), after forwarding the signal it waits for the child to exit and logs
   the child's real exit code; if anything of the segment is still alive after that (a grandchild that outlived it), it says
   so in the log and in its own exit code instead of claiming an end. Keep the detach contract (pid from inside,
   `nohup setsid`, clean-tree check) and the existing rc line format: the tests of the other segments must pass unchanged,
   or you say exactly which expectation changed and why.
3. **The operator can see it.** While a walk is finishing a child after a signal, `launch.sh status` (or whatever the README's
   status mechanism is) and the walk's log say "stopping after <what>", not "ended". `benchmark/launch/README.md` gets a short
   section: what TERM does to each segment, how long the wait can be (a blast's remaining duration plus collection), and what
   to do if the wait must be cut (which process to signal, and that load VMs then need the blast driver's own cleanup
   command — name it from the driver).
4. Tests in `benchmark/tests/test_launch.py` against the fakes (no real sleeps beyond what the existing tests use): TERM during
   a blast → the driver runs to its end, the walk stops with the arm open and the signalled exit code, the rc line comes
   after the driver's last line, both logs (the segment log and the walk's log under `results/<run>/logs/`) hold the stop;
   TERM between children → immediate stop; a second TERM; TERM to a segment that is not `arms` → as today; a grandchild that
   outlives the child → reported, not hidden. Mutation cases for the lines that matter in `benchmark/tests/check_mutations.py`.
