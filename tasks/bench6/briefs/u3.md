## Why
Bench 5 (r20261107-1504) reached 3,449 tx/s against bench 4's 4,578 because the MDBX commit wrote 4.3× the device bytes of the pages
it dirtied (commit 178 of 288.6 µs/tx). Under WRITEMAP a page cache made of large folios is written back a whole folio at a time.
The investigation found why the cache had large folios: every node ran its whole load in a RE-OPENED database (the deploy's
finalize stage starts each node once, which creates the file and grows it to 4 GiB; the real start is the second open), and on a
re-open libmdbx applies its random-access advice only to `[0, used)` — the genesis pages. The edge moves only when the file grows,
and the file never grew. So the whole working range of `mdbx.dat` was mapped without `MADV_RANDOM`.

## Deliver
1. **The advice** (behind `mdbx_random_advice`, default false = nothing is called): after the database is opened, find every
   mapping of THIS environment's `mdbx.dat` in `/proc/self/maps` — match by device and inode of the opened file, not by path (tests
   open many temporary environments in one process) — and `madvise(MADV_RANDOM)` each. libmdbx maps its whole reservation once, so
   one call per mapping covers all future growth; re-apply only if the mapping set changes (check cheaply after a persist: compare
   the mapping list's (start, end) with what was advised; a remap happens only when the upper limit changes). Linux only: on other
   targets the function is a documented no-op that reports 0 bytes. Every `unsafe` block carries a `// SAFETY:` comment (the range
   comes from the kernel's own map of this process; `madvise` with this advice never changes contents). A failed `madvise` is
   logged once at warn and never fails the open.
2. **Proof gauges**: `tn_reth_mdbx_random_advice_bytes` (bytes of `mdbx.dat` mappings successfully advised; 0 with the switch off)
   and `tn_reth_mdbx_used_bytes` (the database's used size = last page number × page size), updated at open and after each persist.
   The used-size gauge is exported with the switch on OR off (the harness sampler reads it).
3. **`persisted output`** gains, as deltas over that one persist, exactly: `page_newly`, `page_cow`, `page_spill`, `page_unspill`,
   `page_prefault`, `page_wops`, `page_msync` (libmdbx's page-operation counters from the environment info) and `proc_write_bytes`
   (the delta of `write_bytes` in `/proc/self/io`); and as current values `mdbx_used_bytes` and `mdbx_advised_bytes`. Plus the
   counter `tn_reth_mdbx_page_ops_total{op}` with `op` ∈ `newly`, `cow`, `spill`, `unspill`, `prefault`, `wops`, `msync`. These are
   read with the switch on or off (they are how the control arm shows the amplification). Reading them must not open a second
   reader or transaction that outlives the call, and must cost microseconds: measure it and say so. If a counter is not exposed by
   the vendored bindings without a vendored edit, stop and report which, with the smallest way to get it.
3b. **Fields added after the local probe run (2026-11-11)** — read `/home/drtnarg/coding/telcoin/devnet-genesis/benchmark/private/bench6-prep/I-1r/verdict.md`
   §5 ("What run 1's control arm must record") before you write the line; it defines each field and what it decides. The probe
   showed that with prefault ON a re-opened database does not amplify and with prefault OFF it amplifies 8.7×, so the control arm
   must be able to tell from the node's own log whether prefault is effectively on. Add to `persisted output`, switch on or off:
   `mdbx_last_pgno` (current value, so Δ against the previous line is the growth in pages: Δ`page_prefault` ≈ Δ`mdbx_last_pgno`
   means prefault on, ≈ 0 while the database grows means off), `freelist_pages`, `gc_entries`, `gc_large_pages` (from the
   environment's freelist count and the stat of the GC table, if the vendored bindings expose them without a vendored edit and
   reading them costs microseconds — measure; if a statistic needs a table walk, leave it out and say so), and
   `prefault_wchar_bytes` exactly as §5 defines it IF it can be done without touching the transaction-manager thread's code under
   `vendor/` (it is a per-thread `wchar` delta; if it needs a vendored edit, leave it out and report). Optional, same rule:
   `mdbx_readahead_enabled`. These names are frozen with the others.
   **Never open the environment a second time and never run or shell out to an MDBX tool**: any open of a live environment without
   `NORDAHEAD` switches prefault off for every allocation through the shared lock file — it would create the effect being measured.
4. Design it so a later unit could add "prefault off" without restructuring (the advice closes mmap read-around at the growth
   frontier but not libmdbx's multi-page prefault write, which can also build large folios; whether that route matters is being
   measured on a probe). Do NOT build that switch; say in the hand-back what it would take without a vendored edit.
5. Separate commit, `Topic: digest-dedupe`: `skipping invalid transaction` gains `sender` (the recovered signer; read it before the
   transaction is moved). No behaviour change.

## Tests
Linux-only tests: after open with the switch on, every `mdbx.dat` mapping of the test environment shows `rr` in `/proc/self/smaps`
and the advised bytes equal the mapping size; with the switch off none does and the gauge is 0; two environments in one process do
not advise each other's files; after writes that grow the database the mappings still show `rr`; page-ops deltas are non-zero after
a persist that dirtied pages and zero after an empty one; `proc_write_bytes` parses. A golden for the `persisted output` field names.
