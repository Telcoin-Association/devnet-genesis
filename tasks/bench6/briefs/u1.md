## Why
In bench 5 (r20261107-1504) the three fastest executors had their headers refused by a quorum of voters as "execution behind"
(0.2 %, 0.0 % and 16.3 % of their headers certified): a proposer names its own execution tip in the header, and a voter refuses a
header whose named block it has not executed yet. The fix on the proposer side is to name a block that a quorum already holds.

## Deliver
The investigation showed that the rule applied to EVERY header settles on the floor (the parents' named blocks are earlier outputs of
the same rule, not tips), so two policies are built behind the switches and the benchmark compares them:
- `quorum_exec_block: false` (default): today's code path, the `Header::new` argument byte-identical.
- `quorum_exec_block: true`, `quorum_exec_block_starved_rounds: 0`: the quorum rule on every header (policy "always").
- `quorum_exec_block: true`, `quorum_exec_block_starved_rounds: K > 0`: name the own tip by default; after one of the proposer's own
  headers is cancelled uncertified (the certifier's existing cancel report), apply the quorum rule for the next K rounds, doubling K
  (bounded by a constant; pick and document it) each time it happens again before a header certifies, and return to the tip when the
  rounds are spent — the return is by rounds elapsed, never by comparing values (a value-based return never fires once several
  nodes are on the rule). A certified own header resets K to the configured value.
The quorum rule itself, exactly as I-4's eleven items constrain it: rank the own tip (counted once, for the own authority) and each
same-epoch, non-genesis parent's named execution block number from OTHER authors by voting power; take the highest number that
holders with ≥ 2f+1 power have reached; cap at the own tip; floor at N = 8 ring entries back (N its own constant; entries, not block
numbers; a short ring floors at its oldest entry; an empty ring keeps today's default); resolve the hash from the OWN ring
(`newest_at_or_below`), never from a parent; fewer than a quorum of usable values → own tip; saturating arithmetic on every peer
value; read the `recent_blocks` watch once per proposal and drop the borrow before any `.await`.
Make the choice a pure function (inputs: own tip, ring view, parents' (authority, power, number) list, committee quorum threshold,
policy state) so the table tests need no proposer. `recent_blocks.rs` gains `newest_at_or_below(n)` and `nth_newest(k)`.
The `header proposed` line gains `exec_block`, `exec_tip`, `exec_basis` with values `quorum`, `tip`, `floor` (plus `starved` when the
adaptive policy is in its K-round window — add it as a fourth field `exec_policy` = `off` | `always` | `tip` | `starved`).

## Tests (unit; you write no e2e)
A table test of the choice function (in step, own node ahead by 1-6 outputs, own node behind, fewer than a quorum of usable parents,
other-epoch and genesis parents ignored, own certificate among the parents skipped, weighted power, a hostile parent naming a huge
number, short and empty rings, cap and floor); ring helper tests; **the multi-round self-feeding test I-4 asks for**: feed the
function's outputs back as the next round's parents for an in-step ten-node fleet over 20 rounds and assert the lag is exactly N
under "always" and 0 under the adaptive policy; the adaptive state machine (cancel → K rounds → tip; repeated cancels double K up to
the bound; a certified header resets); switch off → the header bytes of an existing proposer test are unchanged.
