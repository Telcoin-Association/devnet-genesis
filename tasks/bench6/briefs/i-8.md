# I-8 — what sets the number of transactions in a consensus output

You are investigation **I-8**. Read `tasks/bench6/briefs/i-common-r1.md` first. Candidate 2 of `A7/candidates.md` is yours. Skills: `tn-domain-consensus`, `tn-domain-worker`.

## Why it matters
At full load every validator of run 1 sat at its disk's write limit, and the writes per transaction fall as an output gets larger (pages copied per transaction go as output size to the power −0.375; unit r1-A8). So whatever sets the transactions per output sets most of the rate. No unit owned it. The arms differed widely (non-empty outputs, transactions each, M16): control about 4,800; `v-vote` 3,260; always-on vote form 2,780; `pool-local-r2` 4,530; `pipe` 2,300-2,470; `bound` about 7,000 with more than half of all outputs empty; `gr150` about 8,300 non-empty (figures differ by unit: see `A7/verdicts.md`, each arm's context table).

## The questions
1. The chain from a round to an output: how often a leader is committed, which batches a committed sub-DAG carries, and how the engine's queue (cap 8) and the execution backlog feed back on the proposer, the batch builder and the commit (find the backpressure in the code: what waits when the engine is behind, and what does not).
2. From the run's data, per M16 blast: rounds per second, commits per second, outputs per second (all and non-empty), batches per output, transactions per batch, and the engine queue depth, on one validator first then the fleet median. The units' extracts hold most of it: r1-A2's parsed events (`benchmark/work/bench6-scratch/r1-A2/`, see `P/A2/` scripts for the format), r1-A4e's `P/A4e/execute.json`, r1-A8's `P/A8/outputs.csv.gz`; exported counters in `P/prom-export/` (`tn_primary_headers_proposed_total`, `tn_executor_output_batches_*`, `tn_executor_output_transactions_*`, `tn_engine_queued_outputs`, `tn_node_execution_backlog_outputs`, `tn_engine_empty_outputs_skipped_total`).
3. Then explain each arm's output size by that chain: is the size simply the landed rate divided by a consensus cadence that does not react to load (so a slower engine gets smaller outputs, and smaller outputs make it slower: a loop), or does something else set it? Why did `pipe` have small outputs and the admission bound large ones with many empty outputs between them? Did the always-on vote form shorten rounds, and why?
4. What in the node could make outputs larger at the same landed rate (fewer commits, merging outputs before the persist, a larger batch, skipping empty outputs), each with its code location and what it would cost in latency. Options, no patch.
