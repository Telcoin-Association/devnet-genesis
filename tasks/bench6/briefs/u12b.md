## Why
In bench 5 (r20261107-1504) the engine executed an output (479 ms) and persisted it (1,167 ms) strictly in sequence. Letting
output N+1 execute on N's in-memory state while N's persist runs makes the cycle max(execute, persist) instead of their sum. Unit
U12a built the core: a `PersistPipeline` with two slots, a pinned read snapshot per output, and the build/commit split of the
payload builder. Nothing uses it yet. You wire it into the engine loop behind the switch `pipelined_persist` (default false =
today's strictly sequential loop, verbatim), add its metrics and the test hook the interleaving tests need. The feature ships
in the bench image only if its go/no-go tests pass; yours are part of them.
