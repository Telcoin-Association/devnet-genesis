## Why
`benchmark/tools/arms-summary.py` gives one row per arm of a fleet run. Its storage columns judge a persist by BYTES (device
bytes ÷ bytes MDBX dirtied). The user pointed out, and a one-VM probe on the fleet's disk then measured
(`benchmark/private/bench6-prep/probe/SUMMARY-r20261111-2310.txt`; the gate notes
`/home/drtnarg/coding/telcoin/devnet-genesis/tasks/bench6-g1-notes.md`, section "THE GCE PROBE ON THE FLEET'S SHAPE", items 5 and
6), that on a cloud network disk the binding constraint is not always bytes: healthy commits are bound by the NUMBER of
writes (5,600-14,800 small writes per commit at about 1.3 ms each), amplified ones by the throughput cap (256 KiB writes at
59 ms each against 800 MiB/s). The fleet's disks are provisioned at 20,000 IOPS and 800 MiB/s; if a real output dirties
about 15,000 pages, back-to-back persists cannot run faster than one per 0.75 s whatever the node does — the execution
ceiling may be the disk's provisioning. Run 1 must show this per arm, and today the summary cannot.

## Deliver
1. Per row and node, over the row's measured window, from the persist CSV's device counters: write operations per
   persisted output (`wr_ops_per_output`: Δ`disk_wr_ios_total` ÷ outputs persisted in the window), mean KiB per write
   operation, flush operations per output, sustained write IOPS and MiB/s (Δ ÷ window seconds), device time per write
   operation (Δwrite ticks ÷ Δwrite operations) and per flush; and against the provisioning: `iops_pct_of_cap`,
   `mibps_pct_of_cap`, and `binds` = `iops` | `throughput` | `neither` (which is nearer its cap; `neither` below a
   threshold you state) — plus the row medians across nodes. A peak figure too: the highest one-sample write IOPS and MiB/s
   in the window (the sampler's cadence bounds what a peak means: say so in the column's note).
2. A one-line reading per row in the markdown (under the per-node table, like the storage notes): e.g. "persist is within
   12 % of the provisioned IOPS on 9 of 10 nodes: the disk's IOPS cap bounds this arm", or "no node above 50 % of either
   cap". The wording is derived from the numbers, with the thresholds named.
3. `n/a (missing: …)`, never 0, where the CSV lacks a column or the provisioning is unknown; the device the counters belong
   to must be the one that holds the node's data directory (check how the sampler picks it and state it).
4. Tests in `benchmark/tests/test_arms_summary.py` with a fixture CSV: an IOPS-bound arm, a throughput-bound arm, an arm far
   from both, a node whose CSV lacks the tick columns, unknown provisioning. Mutation cases in
   `benchmark/tests/check_mutations.py` (your own; re-anchor any you move). The bench-5 self-check keeps every existing
   column identical (`python3 benchmark/tools/arms-summary.py --self-check --out-dir <scratch>`, about 3.5 minutes) — and
   since bench 5 has no persist CSV, state what the new columns read there.
