## Why
A benchmark run is a chain of long driver calls against a GCP fleet (deploy ≈ 46 min, blasts, collect, teardown ≈ 35 min, bundle).
In bench 5 each segment was started by a hand-written launcher script that lived in a session's scratch directory (they are now in
`benchmark/launch/bench5/`, untracked, with absolute home paths: read them, they are the model and the reason for this unit — a
background task dies with its session, `$!` of `nohup setsid … &` is the wrapper and not the detached session, and a relaunch
without checking can start a second driver against the same fleet). Bench 6 has two deployments: run 1 walks eight "arms" on one
fleet (each arm = a set of node switches applied by rolling restart, then the same blasts), run 2 is the headline on a fresh fleet.
Both need launchers in the repo, parametrised, tested, and an arm sequencer that can stop safely and resume.

## Deliver (checkpoint after each)
1. **`launch.sh <env-file> <segment> [segment args]`**: starts ONE segment detached and returns at once. Segments: `probe`,
   `deploy12`, `arms`, `blast15`, `step15`, `teardown`, `archive`, `reindex`, `bundle`, `arms-summary` (map each to its driver
   call; take the bench-5 launchers and the plan's W4/W6 sequences as the source). It: reads the env file (plain `KEY=value`
   lines, comments, no command substitution — parse it, do not `source` it blindly) and exports it; refuses a placeholder value
   (the env files ship with `<…>` placeholders for the image digest, the node sha and the run id: the orchestrator fills them at
   the gate); refuses a dirty harness tree (`git status --porcelain -- benchmark/` not empty), a stale gcloud token (a bounded
   `gcloud auth print-access-token`; skipped for segments that need no gcloud), and a segment or driver already running for the
   same run (pid files and a process check whose pattern cannot match itself); starts the segment with `nohup setsid`, writes the
   pid FROM INSIDE the detached shell to `tasks/bench6/<run>/<segment>-<UTC>.pid`, logs to the `.log` beside it, and guarantees a
   final line `== <segment> rc=<n> <UTC>` whatever happens; prints the log path, the pid and the exact line to wait for.
   `--dry-run` prints the command and environment it would start and starts nothing (a separate code path: the live start sits
   behind an explicit guard on the line before it). `launch.sh <env-file> status` lists the run's segments with pid, alive or
   not, and the last line of each log.
2. **`run-arms.sh`** (what the `arms` segment runs): walks `bench6-run1.plan`. For each arm in order: apply the arm
   (`params-apply.sh --from-config --arm-file …`; the control arm changes nothing and restarts nothing), wait until its `ready`
   time, then run the arm's steps — a blast of a given type (fund + run with that type's environment and the next
   `BENCH_RUN_INDEX`), an idle interval recorded with `--mark` / `--end-mark` — then close the arm. Rules from the plan's W4,
   each one tested: a node that fails its restart or readback (`PA_FAIL` / `PARAMS_FAIL`), two guard deferrals, or a tool exit
   ≠ 0 stops the run with the fleet left as it is and a clear last line; a failed blast is retried ONCE (same type, next index),
   then the run stops; before a saturated blast (M16, M4) every node's queued pool must be below a threshold (default 1,000,
   knob `RUN_ARMS_MAX_QUEUED`, 0 = off; read it the way `benchmark-blast.sh` reads `pool_at_start`, or from its `POOL_AT_START`
   line of a zero-cost pre-check if that is simpler — say which): wait up to a bound, then stop; `--from-arm <k>` resumes at arm
   k (re-applying it under a new recorded name, as the arm tool requires) and `--only-arm <k>` runs one; every wait has a
   deadline; it prints one `ARMS_STEP arm=<name> step=<n> kind=<…> rc=<n> <UTC>` line per step and ends with `ARMS_DONE` or
   `ARMS_STOPPED arm=<name> step=<n> reason=<…>` followed by the exact resume command. `--dry-run` prints the whole walk (every
   driver command with its environment) and calls nothing.
   Health stops the sequencer cannot see from exit codes — a `FatalDBFailure` in a node log, a commit stall longer than 120 s,
   a root disk above 85 % — are checked between steps if the harness already has a bounded way to read them (find it: the
   admission gate and the stall scan read such things); what has no cheap check is listed in the README as the orchestrator's
   watch item, not silently dropped.
3. **`bench6-run1.plan`**: the default schedule of the plan's W4 table in a line format you define and document (arm file, then
   its steps), editable by hand because the user fixes the final table at a gate: A0 control (idle, L, M4, M16) → P1 (M16) → V (L,
   M16) → POOL+LOCAL (M16 with an epoch boundary inside the mixed phase: say how the step is timed against the 1,200-s epoch) →
   PIPE (M4, M16) → BOUND (M4, M16) → GR150 (idle, L, short M16) → A0′ (M16). Blast types as the plan defines them (L 8 × 16;
   M4 600 × 4; M16 600 × 16 without chaos, 120 / 480 / 180 s plus the tail scan; I 5 idle minutes). A test parses the plan and
   checks every arm file exists and every step type is known.
4. **Env files**: `bench6-run1.env` (the arms run: bench-5's launch block with placeholders for run id, image digest and shas;
   `BENCH_NODE_BOOT_IMAGE` pinned; `BENCH_PERSIST_SAMPLER=1`; `BENCH_TAIL_SCAN_SECS=180`; `BENCH_LIGHT_START_DELAY_SECS=150`;
   `BENCH_TEARDOWN_SKIP_ARCHIVE=1`; no chaos), `bench6-run2.env` (the headline: as the plan's W6 block — `BENCH_ARM_FILE=benchmark/arms/final.arm`,
   `BENCH_CHAOS=1`, `BENCH_DURATION_SECS=2400`, `BENCH_LIGHT_LOAD=1`, `BENCH_LIGHT_SENDERS="8 600"`, `BENCH_LIGHT_WINDOWS="16 4"`,
