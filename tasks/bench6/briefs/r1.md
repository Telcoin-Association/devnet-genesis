# R1 — a fund that timed out short must not read as a success (defect R1-D5)

You are unit **R1**. Read `tasks/bench6/briefs/r-common.md` first, then the section "R1-D5" of the defects file it names.
Checkpoint: `tasks/checkpoint-bench6-R1.md`. Budget: under 150k tokens.

## Why
In run 1 two funds (indices 3 and 15) logged `prepare: timed out waiting for top-ups to land still_short=2200` (and `1600`), the funder still printed `BENCH_FUND_DONE rc=0 reason=ok`, the fund step printed `✓ funded`, and the two blasts ran with 3,800 and 4,400 of 6,000 senders (generators logged `senders without native balance skipped … unfunded=N`). Run 2 is one long headline blast: a short fund there would spoil the run.

## You own (and write nothing else)
`benchmark/benchmark-blast.sh` (the fund path only: `do_fund` and what it calls), the test module(s) that cover the fund path (find them: `grep -ln 'do_fund\|BENCH_FUND_DONE\|fund --yes' benchmark/tests/*.py`; add a new module `benchmark/tests/test_fund_short.py` if none fits), fixtures you add under `benchmark/tests/fixtures/`, and the one README paragraph that describes the fund step if `benchmark/README.md` or `benchmark/launch/README.md` has one (only that paragraph).
Not yours: the generator repo, `run-arms.sh`, `check_mutations.py`, `make_bundle.py`.

## The change
1. After the funder's output is copied locally, read `still_short=<n>` from the funder's generator log (the newest value when the line repeats). Real evidence to build the fixture from, read-only: `benchmark/results/r20261112-1520/funder-3-*/` and the top-level `benchmark/results/r20261112-1520/funder/` (index 15), and a healthy one, `funder-2-*/`. Copy only the few lines you need into a fixture; no instance id or IP in it.
2. When `still_short` is above 0: print one `⚠` line that names the index and the count, record it in the manifest under the existing fund record of that index (look at how `.fund` and `.blast_runs[]` are written today and at `benchmark/report/make_bundle.py`'s list of known manifest keys before choosing where: a new top-level key would be refused by the bundle; say in your hand-back exactly which key you used and why it is safe), and run the prepare ONCE more (the funder counts `already_funded=` and tops up only the rest). After the second prepare read `still_short` again: 0 is success with a note; above 0 the fund step fails with a reason `fund-short-<n>` (the walk's retry and stop rules then apply; do not touch them).
3. A knob for the old behaviour is NOT wanted. With no `still_short` line or `still_short=0` everything is byte-identical to today.
4. Optional, only if it is one line and tested: the done poll `BENCH_FUND_POLL_SECS` default stays 60 (do not change defaults; note in the hand-back that 15 would save about half a minute per fund).
