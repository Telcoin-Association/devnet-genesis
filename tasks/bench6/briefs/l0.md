At gate G1 the user added a short extra deployment to bench 6: the same ten-validator fleet with each node's database on a **local NVMe SSD** instead of the 100 GB Hyperdisk Balanced disk, run for the control arm (with and without page-cache eviction) and the `MADV_RANDOM` advice arm, to compare disk classes under sustained load.

The harness today creates one shape for all ten nodes (`MACHINE_TYPE`, `NODE_DISK_TYPE` in `benchmark/config.sh`), and the node's data directory sits on the attached Hyperdisk.
The probe driver already formats and mounts a local SSD on one VM (`benchmark/benchmark-probe.sh`, its `setup` step and the `--disks both` path): reuse its mkfs and mount options and its way of finding the device.

**The shape is not decided.** No single x86 local-SSD machine type exists in all ten of the fleet's zones (handoff §6.3 has the table). The user chooses at gate G2 between: (a) a mixed C3/C4 local-SSD fleet in the ten present zones (us-west2-a has neither: that validator moves or the fleet has nine); (b) `c4-standard-8-lssd` in eight zones with two validators moved; (c) a smaller fleet on `c3-standard-8-lssd` (seven regions, validator 02 moved inside europe-west2); (d) other regions for this deployment.
So the harness change must not bake one option in: it needs a **per-node machine type** and it must work with the existing per-node zone list (`ZONES`, `BENCH_ZONE_FALLBACKS`, `zones.env`). Say what a fleet of fewer than ten validators would take (genesis, committee, blasters, the readers) and whether the harness already supports it; do not design it in detail if it is expensive, just price it.
The Hyperdisk comparison arm should be able to run on the same machine shape as the local-SSD nodes (for example `c3-standard-8` + Hyperdisk against `c3-standard-8-lssd`): check that `BENCH_MACHINE_TYPE` alone already gives that.
