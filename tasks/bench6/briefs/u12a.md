## Why
In bench 5 (r20261107-1504) the engine executed an output (479 ms) and persisted it (1,167 ms) strictly in sequence. Letting output
N+1 execute on N's in-memory state while N's persist runs makes the cycle max(execute, persist) instead of their sum (a ceiling of
×1.41 at those numbers). This is the one large change of the round. It ships behind `pipelined_persist` (default false = today's
strictly sequential path, untouched), last in the cherry-pick order, and only if its go/no-go tests pass.

## The invariant that matters most
I3, the overlay anchor: every state root of N+1 must read ONE snapshot pinned just before persist(N) is spawned, so it always sees
the database as of N−1. If a root opens a fresh read transaction and persist(N) commits mid-build, N's deltas are layered over a
database that already holds them; the emitted trie updates can then differ even when the root matches, and the next persist writes
them to disk. `test_pinned_anchor_root_ignores_later_commit` pins it: write it first.
