## Part A — parent-grace

### Why
At light load in bench 5 (r20261107-1504) the two far validators (London and the Netherlands) had only 13-18 % of their own
certificates committed: the near validators reach a quorum of parents and propose the next round before the far ones'
certificates arrive, so those certificates are parents of nothing and are never committed. A proposer that waits a short, bounded
time for the parents it used last round, before proposing without them, lets the far certificates in. Upstream issue #1803 (and
the same proposal as variant 2 of #1781).

### Deliver (behind `parent_grace`, zero = today's path, byte-identical decisions)
When the proposer is ready to create a header (the existing condition is true) and the max-delay path did not fire: compute
`missing` = the authors of the round r−1 certificates that this node used as parents in its LAST header, minus the authors already
present among the parents collected for the new header. If `missing` is empty, propose as today. If not, arm one deadline at
`now + G` (G = `parent_grace`) and keep collecting: propose as soon as `missing` becomes empty or the deadline fires, whichever
comes first. Constraints that keep it a bound and nothing else: the max-delay path stays unconditional and always wins; a grace is
armed at most once per round; a parent set below quorum never proposes (as today); the grace never delays a proposal past
`max_header_delay`; an author that was not in the last header's parents is never waited for; with G = 0 no timer is created.
State what happens at the first round of an epoch and after a round in which this node did not propose (no "last header" to
compare with): the conservative choice is no grace.
Metrics (exact names; say them in the hand-back): histogram `tn_primary_parent_grace_wait_seconds` (time actually waited, only when
a grace was armed), counter `tn_primary_parent_grace_total{outcome}` with `outcome` ∈ `complete` (all missing authors arrived),
`expired` (the deadline fired), `preempted` (the max-delay path or a round advance ended it), and counter
`tn_primary_late_parents_total{origin}` where a parent certificate for an older round arrives after the proposal (`origin` = the
static label the code can give cheaply: at least `own_round_behind`; do not label by peer id). The `header proposed` line gains
`grace_ms` (0 when no grace was armed) and `parents` if it does not carry the parent count already.

### Tests (paused clock)
The issue's cases: all of last round's authors present → proposes at once; one missing author arrives after 40 ms → proposes then
with it; never arrives → proposes at G without it, outcome `expired`; max-delay fires during the grace → proposes then, outcome
`preempted`; G = 0 → no timer, today's timing; an author absent from the last header is not waited for; below quorum never proposes;
at most one grace per round. Each by name three times.

## Part B — the voter cases of quorum-exec-block (tests only)

Unit U1 made a proposer name an execution block older than its tip (up to 8 outputs back) when `quorum_exec_block` is on. The voter
side needs no code change, but two behaviours must be pinned by tests because the fix relies on them
(`/home/drtnarg/coding/telcoin/devnet-genesis/benchmark/private/bench6-prep/I-4/unit-specs.md` §U1 item 11):
1. a header that names an OLD block the voter has executed is voted for WITHOUT waiting, including when that block has already
   left the voter's recent-blocks ring and must be confirmed from the canonical database;
2. a header that names an old block NUMBER with a DIFFERENT hash than the voter executed is refused with the existing
   `UnknownExecutionResult` (`unexpected execution result received`), not treated as "behind".
Add them to `crates/consensus/primary/src/tests/network_tests.rs` at the end, under `// ---- bench6 quorum-exec-block voter cases ----`,
following the paused-clock vote tests unit U2 added there (run each with `vote_queue_fix` off and on: the answers must be the
same). You own only those new tests in that file; do not change `handler.rs`. If a case cannot be expressed because the check
does not behave as described, do not "fix" the handler: report it — it would be a finding for the proposer fix.
