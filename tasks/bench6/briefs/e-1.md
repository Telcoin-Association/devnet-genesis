# E-1 — did every epoch record close with a quorum, and on the same state? (the runs' data)

You are investigation **E-1**. Read `tasks/bench6/briefs/e-common.md` first.

## The question
For every epoch close of run 1 and of run 2, from the logs and exported metrics of all ten validators (and the observer where it shows something the validators do not):

1. The record's certificate: on each validator, the `epoch record quorum` line (`epoch`, `signers`, `committee`, `timeouts`, `missing=[…]`, `epoch_hash`) and its time after the close. Did every validator collect or receive a certificate for every epoch? With how many signers (the quorum is 7 of 10)? Which closes had no margin (exactly 7), who was missing, and what was each missing validator doing at that moment (execution lag, late entry into the new epoch, down)?
2. Agreement: is the `epoch_hash` the same on all ten validators for each epoch, and is the final execution state behind it (block number and hash) what each validator itself executed at the close? Any vote or record for a different hash, any `epoch record` warning or error, any line of the state check (`tn_node_epoch_record_state_check_skipped_total`, `tn_node_epoch_record_vote_skipped_total{reason}`, `tn_node_epoch_record_missing_signers_total` in the exports; grep the node code for the log messages around `check_stored_record_final_state` and the vote path in `epoch_votes.rs` before you grep the logs, so you search for the real strings).
3. Timing against execution: at each close, how far each validator's execution was behind the last committed output of the epoch when it voted on the record, how long the record took from the close to its quorum, and whether the next epoch's first headers and commits waited for it.
4. The comparison the user asks for: the same table split by the vote fix's state at that close: off (`a0-control`, `p1-mdbx-advice`, `a0-prime`), adaptive (`v-vote`, `pool-local-r2`, `pipe`, `bound`, `gr150`), always-on (`v-vote-floor-r2` and all of run 2), and by loaded or idle. Is there any sign that the fix changes how many validators sign, how late the record certifies, or whether the validators agree on the final state?
5. Run 2's boundary inside the outage (epoch 5 opened 15:41:58Z with validator-05 down since 15:40:59Z): the record of the epoch that closed then (signers, missing, time), validator-05's record handling when it came back (did it obtain the certified records it missed, by which path, and did its own state agree), and the first close after its return.

Arm intervals of run 1: `benchmark/results/r20261112-1520/manifest.json` `.param_arms[]`. Epochs last 1,200 s. Blast windows: `.blasts[].phases` of each manifest.
Start from r1-A3's `scripts/boundary.py`, `aggregate_boundary.py`, `prom_boundary.py` and its extracts; extend them to the record's vote and certificate lines and to run 2.

## Deliverable
`findings.md` with one table row per epoch close per run (epoch, time, arm or run, fix state, loaded or idle, signers min / median / max over the validators' quorum lines, missing validators, hash agreement yes or no, seconds from close to quorum, anything abnormal), the split of question 4, the account of question 5, and a plain answer to: did every epoch record of these runs close with a quorum of validators on one state, and how close to the quorum's edge did it come?
