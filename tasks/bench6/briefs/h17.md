## Why
`benchmark/benchmark-probe.sh` creates ONE GCE VM, runs the MDBX write-back probe binary through a table of arms, pulls the
results and deletes the VM. It exists to answer a question the fleet cannot answer cheaply: why bench 5's MDBX commit wrote
4.3 device bytes for every byte it dirtied, and whether the planned fix (whole-map `MADV_RANDOM`) removes it. Three things
have changed:

1. **Its first live run stopped at setup** (run r20261111-2203, log
   `tasks/bench6/r20261111-2203/probe-20261111T220400Z.log`: `SETUP_FAIL no fincore`; the VM and disk were deleted, `DOWN_OK`).
   The pinned boot image (`ubuntu-2404-noble-amd64-v20261105`) has no `fincore` (on Ubuntu 24.04 it lives in
   `util-linux-extra`), the VM has no external address, and a comment in `bench-lib.sh` says the image ships it. The persist
   sampler and the host probe already fall back to the census tool's `--resident-only` (an untouched mincore map); the probe
   driver's setup and its safety arm require the binary.
2. **The user's point about disks, which changes what the probe must report:** a local NVMe disk handles hundreds of
   thousands of small writes per second, so scattered 4 KiB writes cost almost nothing and BYTES are the measure; a cloud
   network disk (Hyperdisk: the fleet's is provisioned at 20,000 IOPS and 800 MiB/s; others in the project at 4,500) caps
   the NUMBER of writes and pays about 1 ms per sync, so the write count is the measure. The fix under test trades bytes
   for operations (a few large whole-folio writes become many 4 KiB writes): on an IOPS-capped disk that may not shorten a
   commit, and may lengthen it. A byte ratio alone cannot show which.
3. **The user wants NVMe compared with Hyperdisk.** The cheapest clean comparison is one VM with both devices, so that only
   the device differs.

## Deliver
1. **No hard dependency on `fincore`.** Setup no longer fails without it; wherever the driver reads a file's resident pages
   it uses `fincore` when present and otherwise the bundled `folio-census.py --resident-only` (state which was used in the
   manifest and in `SUMMARY.txt`). The safety arm must still prove its point (five censuses as root leave residency
   unchanged) with either reader — say whether the fallback reader can itself disturb what it measures, and how the arm
   guards against that. Then check EVERY other tool the setup requires or the arm scripts call against what a stock
   Ubuntu 24.04 minimal cloud image carries (`systemd-run`, `findmnt`, `lsblk`, `timeout`, `sha256sum`, `python3` and each
   python module the census imports): list them with the package each comes from, and carry or replace any that is not in
   the base system. Fix the wrong comment in `bench-lib.sh` (`_bench_host_py`: "the image ships … fincore") — that one line
   only.
2. **Write counts beside bytes, per arm.** `SUMMARY.txt` and the manifest's per-arm record gain, as medians per output over
   the arm's measured outputs (and totals): device write operations, mean and p90 write size, flush/sync operations,
   device write time if the source has it, next to the existing bytes ratio and commit time; and one derived line per arm
   that names the binding constraint on THIS device — write operations per second against the provisioned IOPS, bytes per
   second against the provisioned throughput — so that a reader sees at once whether an arm with fewer bytes paid for it in
   operations. Take the numbers from what the probe binary and the sampler already record (`/proc/diskstats` deltas);
   `n/a` where a source lacks one, never 0. The existing columns and their order stay (append).
3. **A second device on the same VM** (`--disks hyperdisk` is today's behaviour and the default; add `--disks both`):
   with `both`, the VM is a shape with local NVMe SSD (find the right C3 shape from the documentation you can reach
   offline — `gcloud compute machine-types` cannot be called by you; `c3-standard-8-lssd` is the orchestrator's guess: verify
   the name pattern in the repo's own notes or say you could not), the local SSD is formatted (ext4, the mount options the
   fleet's data disk uses: find them in the deploy path) and mounted, and each selected arm runs twice — database on the
   Hyperdisk, database on the local SSD — as two records `<arm>@hyperdisk` and `<arm>@nvme`, with `SUMMARY.txt` pairing them.
   An `--arms` subset keeps the run inside the deadline: propose the subset that answers "does the fix help or hurt on each
   device" (at least: the node-default growth arm, its prefault-off control, each with whole-map `MADV_RANDOM`, and the
   no-WRITEMAP arm) and its duration. The delete path must remove everything it created (a local SSD goes with the VM;
   prove from the code that no extra disk resource is left) and the label checks stay.
4. **Shim tests first** (the repo's rule: a creation script is shim-tested before it is ever run live): the fake gcloud
   covers the new shape and flags; the plan golden is regenerated and READ (say what changed in it); tests for setup
   without `fincore`, for the summary's new columns (including `n/a`), for `--disks both` (two records per arm, pairing,
   the mount), and for a failed local-SSD mount (the run fails closed and still deletes the VM). Mutation cases for the
   lines that matter.
5. A short section in `benchmark/launch/README.md`'s "The probe": the two modes, the knob (`LAUNCH_PROBE_DISKS` or however the
   launcher passes it — add it to `launch.sh` if needed, with its test), what each run costs in minutes.
