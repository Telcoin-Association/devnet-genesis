## 4. Dead peer (v05)
- Vote task to v05: network/mod.rs:452-460 send_request -> network-libp2p consensus.rs:1197-1210: PeerMissing immediately if no address, else libp2p dial; DialFailure/ConnectionClosed/Timeout come back as Outbound errors (1551-1622), all retryable in request_vote (only RPCError is fatal, certifier.rs:191-221). Request timeout 10s (config/src/consensus.rs:448 LIBP2P_REQUEST_TIMEOUT). So the v05 task never ends on its own; it ends only via Canceled.
- Certifier returns as soon as weight >= 7 (certifier.rs:338-341); it never waits for v05. A hung v05 request cannot delay quorum and is not what cancels anything.
- v05 matters only through margin: 7 of 10 with 9 live means each header tolerates at most 2 non-voting live peers (3 before the crash). 1 crash + 3 uncertifiable honest headers = 4 > f=3 -> round cannot complete. v05's return added a fresh certifiable header (its own) = the 7th cert.
- Worker batch fetch only walks connected peers (worker/src/network/handle.rs:190-290), so v05 is not in that path after disconnect.
- "Could not form a certificate" needs every vote task finished; the v05 task only finishes via Canceled, so each occurrence is: notify -> rx_votes picked over cancel_proposal for every queued result incl. v05's Canceled. Probability per cancellation ~ (1/2)^(k+2) for k still-outstanding tasks: seeing it at all over ~600 re-proposals means k was small at cancel time, i.e. most peers had ALREADY answered (votes or permanent errors). Diagnostic: count per node N(re-proposing) vs N(Could not form) vs N(fatal request for requested vote).
