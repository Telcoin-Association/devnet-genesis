### Mechanism on main

On main at 45dce8947 the proposer keeps a FIFO lane of digests per worker (`crates/consensus/primary/src/proposer.rs:139`), and each new header drains the lanes' fronts (`:974-999`).
Two paths put an older own header's digests back at the front (`:950-954`): a cancelled header (`:902-921`) and a header the commit rule skipped (`:847-862`).
Both run after a newer own header drained that worker's next digests; payload order is execution order, so the sender's later nonces execute first, are skipped as `nonce too high`, and return to no pool.

### The two pool-side switches

Bench 6 built (A) as `sealed_tx_keep` and (B) as `digest_dedupe` and tried both in an arm walk (r20261112-1520), in one confounded step with other changes and an epoch boundary.
The keep removed every gap resend and unlanded transaction, but it re-sealed each skipped transaction behind its sender's later nonces, which then failed too: 19 % of output transactions were not executed, copied pages per transaction rose about 1.22 times, and duplicate digests appeared.
The dedupe's counters stayed at 0; neither is on main or being ported.

### What we will try

This changes the body's proposal: it preferred (A) and rejected holding nonces at the builder, which allows one batch per sender per commit cycle.
The approach in preparation holds at the proposer by DAG ancestry: a new header takes no digest of a worker while an older own header carrying that worker's digests is not proven its ancestor, so nothing waits while the own chain is intact.
It changes header contents only, not timing or validity, behind a switch off by default.
It is untested; we will measure it in the next run before a PR.
