Bench 6 data for this issue: what put the nodes into the whole-folio state, a fix measured in four runs, and why the issue may not apply to main's default build.

### What starts and ends the state

We traced it in an arm walk on the bench-6 fleet (r20261112-1520: nine node configurations applied one after another by rolling restart; it has no public page).
Every node entered it in its first process that executed blocks: from output 9 on, pages ahead of the allocation frontier, past the range libmdbx advises `MADV_RANDOM` at open, were already cached, so libmdbx skipped most of its prefault writes (it prefaulted 125 of 677 grown pages) and new pages landed in order-4 and order-5 folios.
A restart ends it: the open discards the file past its used size (`mdbx.c:20581-20590`), and later processes prefaulted 1.00-1.52 times their growth.
The observer, never restarted before load, wrote 6.5-10.9 times its page bytes.
What opens the window is a correlation; whether bench 5's nodes blasted in that first process was not checked.

### The fix, measured

The four headline runs applied whole-map `MADV_RANDOM`, re-applied whenever the map size changes (fix (a) above), from the coordinated start, the first process that executed blocks (each node had first run alone during staging, every switch at its default, no output executed): [r20261113-1351](https://benchmark.telcoin.network/runs/r20261113-1351/) and [r20261113-2118](https://benchmark.telcoin.network/runs/r20261113-2118/) at 20,000 provisioned IOPS, [r20261113-1630](https://benchmark.telcoin.network/runs/r20261113-1630/) and [r20261114-0000](https://benchmark.telcoin.network/runs/r20261114-0000/) at 50,000.
Every process prefaulted 1.000-1.025 times its growth in every blast, no folio above order 3 appeared, and at full load the validators wrote 1.16-1.19 device bytes per page byte MDBX copied or allocated.

### Bytes against write count

With the bytes gone, the 20,000-IOPS disk binds on write count.
In r20261113-1351 the validators wrote 19,967 times per second for 40 minutes (0.998 of the limit), 3.74 writes of 5.0 KiB per transaction, against bench 5's 0.68 writes of 227 KB.

### On main at 45dce8947

The execution store is tn-lmdb by default (#1834), with MDBX behind the opt-in `mdbx` feature (`crates/tn-reth/Cargo.toml:157-161`).
tn-lmdb advises every mapping `MADV_RANDOM` on Linux, remaps included (`crates/tn-lmdb/src/file.rs:826-839`, `crates/tn-lmdb/src/env.rs:397`), which closes this route by default (read from code, not measured on a fleet).
The advice switch exists only on bench 6's branch and is not being sent as a PR.

On a provisioned-IOPS disk the write count binds for any engine, so a tn-lmdb run should report device writes per transaction too.
Main's default `--db.gap-fill auto` on Linux (`crates/tn-reth/src/cli.rs:112-119`) trades bytes for fewer writes there; it is the first setting to measure.

For the `mdbx` build, one caution about the sampler proposed above: a stock `mdbx_stat` opens without `MDBX_NORDAHEAD`, which turns the node's prefault writes off (read from code: `mdbx.c:22486-22500`), and a local probe with prefault switched off wrote 8.7 times its page bytes, against 1.00 with it on.

### The issue itself

Two options for the maintainers: close it as not applicable to the default engine, or keep it for the `mdbx` feature, where the defect stands and fix (a) is the measured remedy.
