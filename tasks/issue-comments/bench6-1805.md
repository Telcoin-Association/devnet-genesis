Bench 6 data for this issue: option (A) was built behind a switch and measured on a quiet host and in one fleet arm; the fleet verdict is inconclusive, and the pool is not being ported to main now.

### Quiet-host contention bench

A Criterion bench built a 6,000-transaction, 20-block output on the validators' CPU shape (4 cores × 2 threads) while 0, 1 or 2 recovery jobs for other outputs started with it.

| jobs | `finish`, shared pool (µs/tx) | `finish`, dedicated 3-thread pool |
|---|---:|---:|
| 0 | 3.03 | 3.09 |
| 1 | 11.07 (+8.04) | 3.40 (+0.30) |
| 2 | 19.45 (+16.42) | 3.64 (+0.55) |

On the shared pool the added `finish` time was 95-98 % of the job's wall time.
The dedicated pool removes that wait (`finish` passed the 15 % line with one job and missed it with two, at +17.7 %, which the loop case at the same load passed), but the cost moves: the state root rose 7-16 % while the job ran beside it, outside the 5 % pass line above.

### The arm on the fleet

`recovery_threads=3` ran in an arm walk on the bench-6 fleet (r20261112-1520: nine node configurations applied one after another by rolling restart; it has no public page), whose switches are cumulative: it was switched on with three other switches, and with the vote fix back to its adaptive form, across an epoch boundary.
`finish` fell from 16.9 to 7.3 µs/tx and returned to 15.1 when the global pool came back.
The job took 21.1 µs/tx against 13.6, but with full queues the engine waited only 0.5 µs/tx.
The root rose 15.4 µs/tx (the arm's higher fault rate explains 3.5-7.7; the rest appeared with the pool), so execute rose net from 99.6 to 107.2.
The pool, the cache state and the database size changed together, so the verdict is inconclusive, and the headline runs left the switch off.

### The headline runs, without it

In [r20261113-1630](https://benchmark.telcoin.network/runs/r20261113-1630/) (50,000 IOPS) `finish` ranged from 13.6 µs/tx on the validator whose queue drained to 19.2 on one at the cap, and that costliest engine set the fleet's executed rate.
[r20261114-0000](https://benchmark.telcoin.network/runs/r20261114-0000/) shows the same `finish` spread (15.1 µs/tx on a drained queue against 19.1-19.8 at the cap).
That fits this issue's contention, with the queue as the trigger; it is a correlation, not traced per output.

### On main at 45dce8947

Unchanged: each queued output's recovery job runs on the global rayon pool (`crates/engine/src/lib.rs:247-252`, `crates/tn-reth/src/env/execution.rs:240-258`), and `finish` hashes on the same pool (`execution.rs:435`, `:470`).
Changed by #1834: the state root's storage-root tasks also run on that pool and fall back to serial when it is busy (`crates/tn-reth/src/env/output_overlay/parallel.rs:1-30`).
So on main a recovery job can also cost the root its parallelism, and a dedicated pool would compete with those tasks for the same cores.
Both are read from code; the bench-6 figures, from an MDBX build without the parallel root, do not carry over.
