# Bench 7 report: r20261115-1131 (always-on) and r20261115-1653 (adaptive) at 20,000 IOPS

Two fleet runs on 2026-11-15 on one build, node commit 91a15e223 (image `adiri@sha256:15acdccafff7…68822c`), with ten validators and one observer, each node on a 100 GB Hyperdisk Balanced at 20,000 IOPS [RF 7a] [RF 7b].
Run 7a ran the always-on vote form and run 7b the adaptive form, the arms' only difference (`quorum_exec_block_starved_rounds` 0 and 4); both ran with the order hold and the three epoch-record switches on, and with the closing-block check, which has no switch [RF 7a] [RF 7b] [orch l.99].
Read next: the form comparison, `benchmark/private/bench7-r20261115-1653/A9/comparison.md`; its recommendation, `benchmark/private/bench7-r20261115-1653/A9/recommendation.md`; the bench 6 comparison, `benchmark/private/bench7-r20261115-1653/A10/vs-bench6.md`.
One run stands in each cell throughout: a difference inside run 7a's own spread is not told apart from noise, and no row carries a significance test [C recommendation].

### The metrics agent loses one batch per scrape on some nodes

The operator's session read validator-09's agent config during run 7a [O 14:28Z].
The vendored agent scrapes the node, sets `network` to the chain's name on every series, and remote-writes the result [O 14:28Z].
That overwrites the node's own `network` label (`primary` or `worker-0`), so about 910 series pairs get identical label sets and timestamps, about 110 of them with different values [O 14:28Z].
On validator-09 the remote write logged a rejected batch every scrape: "duplicate sample for timestamp …; overrides not allowed: existing 0, new value 1" [O 12:40Z].
The rest is the explanation, not reproduced: inside one remote-write request Prometheus drops the second of such a pair silently [inferred] [O 14:28Z].
When a pair with different values straddles the boundary between two 2,000-sample batches, the later request meets a committed sample and Prometheus rejects that whole batch, on every scrape [inferred] [O 14:28Z].
Which batch is hit depends on the order in which the node process exposes its series (hash order per process), so it changes when the process restarts [inferred] [O 14:28Z].
In run 7b validator-05's missing series came back after its restart [O 19:28Z].
In run 7a validator-09 lost about 737 samples every 15 s, 102,244 of 658,244 (15.5 %); restarting its agent did not help, and validator-08 lost a batch three times at start-up and then never [O 12:40Z].
The run log says, with no evidence of its own, that bench 6's run 3 (`r20261113-2118`) lost a validator's vote-stage series the same way [O 14:28Z].

## 6. Open questions and what a next run could test

Each item: the question, what would answer it, and the section it comes from.

1. Would a second run of each form keep the recommendation?
   Run 7a's spread is variation inside one run, not between runs.
   Rows inside it could flip: fleet certification (spread 93.37-97.29 %) [C Q1.09], the lowest validator (55.2-89.3 %) [C Q1.10], rounds with four or more under-held headers (0.0-27.9 %) [C Q1.28] and committed rounds per second [C Q1.24]; the two rows against the adaptive run, blast 2's seen p95 and blast 0's rate, could fall inside a second run's spread [C Q1.06, Q1.04].
   A second run of each form on the same build and disk answers it (§4.1).
2. The 50,000 IOPS disk.
   Bench 6 found the adaptive form ahead on certification there and behind on the senders' cost; bench 7 made no run on it, so which cost counts more stays open there (§4.1).
   A pair of runs at 50,000 IOPS on this build answers it.
3. What the named block's age costs.
   Bench 7 measured the distance from the tip to the named block, 7.57 / 4.83 block-bearing outputs [C Q4.21], and a lower bound on the block's age, 7.36 / 4.43 s [C Q4.23], but not what that age costs (§4.1).
   If the age costs something, the fresher block is a reason to make the adaptive form the default.
4. The floor at 16 outputs against 8.
   The per-header analysis's arithmetic predicts no under-held header in either run at a floor of 16 [7a A3 perheader floor] [7b A3 perheader floor]; that is arithmetic on these runs, and only a run at the deeper floor tests it (§4.3).
5. What lowers the far validators' committed share.
   In blast 1 bench 7 committed 2.12-3.50 % of the certificates of validators 02 and 06 against bench 6's 3.96-6.49 % [V q3_far_validators B1.committed_share_pct], and no counter isolates the vote-handler rework, the near validators' speed on the new storage engine or the round rate (§4.5).
   A field on `header proposed` naming the parents a header names would turn the inferred last step of §4.5 into a measurement; the far validators' missing leader slots in blast 1 [V q3_far_validators B1.leader_share_pct] would need the schedule's reputation scores logged beside them.
6. What separates the upstream vote-handler rework from the hold's cadence.
   Both moved together in both bench 7 runs, with the voters' execution lag on the new storage engine, so the fall in certification and the hold's cost are not separable between them (§4.2, §4.3).
   One run with the hold switched off and one without the rework, on this build, would separate them.
7. The hold's early-trigger candidates are inferred, not measured (§4.2).
   The review proposed a field for the un-held count on the `header proposed` line (`pending_unheld`) [review 06 line 318] [7a A7 early_trigger]; with it, a run would count them.
8. The engine's sequential cycle as the ceiling.
   Bench 6's statement that at 50,000 IOPS the engine's sequential cycle sets the ceiling cannot be tested on bench 7: both runs were at 20,000 IOPS, where the engine was busy 978.1 / 978.4 ms per second and the device ran at 0.8591 / 0.8628 of its write cap [V q7_statements 1. line 60].
   Bench 6's statement that a faster configuration (a faster disk, pipelined persist, group commit) widens the engines' spread is listed as untestable too [V q7_statements 4.3 line 386] (§4.4).
   A run at 50,000 IOPS on this build answers the first; the second also needs the engines measured side by side on the same configurations.
9. The two recovery items measured and not explained (§4.7).
   Validator-05's first own certificate after its promotion committed after 1.65 s in run 7a and 59.6 s in run 7b [7a A4 recovery own_after] [7b A4 recovery own_after]; the parents field of item 5 would show whether the near validators named its first certificates.

10. The metrics agent's defect.
    Validator-09's Prometheus series in run 7a and those of three validators and the observer in run 7b are partial [RF 7a] [RF 7b] [7b A5 engine.md T17] [7b A6 export_coverage]; the run notes put it down to the metrics agent losing one remote-write batch of every scrape [RF 7a] [RF 7b].
    The units used per-minute endpoint samples as stand-ins (§2, §5); fixing the agent before the next run removes the need.
11. The switches nothing triggered.
    The conflict halt (`epoch_record_conflict_halt`), the re-certify round (`epoch_record_recertify`) and the walk past an uncertified epoch (`epoch_record_collect_past_uncertified`) were on in both runs and never fired (§4.6).
