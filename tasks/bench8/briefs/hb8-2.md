# HB8-2 — the run chain: credentials, the idle check's `up` rule, the endpoint sampler as a segment, the export check

Common brief: `tasks/bench8/briefs/hb8-common.md`. Checkpoint `tasks/checkpoint-bench8-HB8-2.md`.

Bench 7's orchestrator scripts live under `tasks/bench7/` and are the record of how bench 7 ran: do not edit them. Nothing under `benchmark/`.

1. Credentials. The chain's preconditions (plan mode and live) check that `gcloud auth print-access-token` succeeds and print the login's age if it can be read (say how: the credential store's file time, `gcloud auth list`, or "unknown"). Before `blast15` it checks again. A run needs about 3 h of valid credentials and a login lasts just under 5 h: refuse the launch (new exit code) when the login is older than a threshold (`CHAIN_LOGIN_MAX_AGE_SECS`, default 3,600) or its age is unknown and `CHAIN_LOGIN_AGE_UNKNOWN_OK` is not 1. While waiting on a segment, a failed token refresh is reported as `CHAIN credentials …` with the fleet's state ("the fleet is UP: run `gcloud auth login`, then …"), not as a failed blast: the lost run's driver log said "Reauthentication failed. cannot prompt during non-interactive execution"; match that and the usual refresh errors in the segment's log.
2. The idle check's `up` rule. In all three bench 7 fleets the chain stopped because `up` was missing for a healthy node (a defect of the metrics agent, reported upstream: its remote write loses one batch per scrape on some nodes, `up` among the lost series). New rule: a node passes when `up == 1` in Prometheus OR its own metrics endpoint answers through the path the endpoint sampler uses and shows the node's mode and switches; the chain prints which nodes passed by the fallback and goes on. Modes and switches are still required for every node, from Prometheus or from the endpoint. Bench 8 adds one count to the switch check: `quorum_exec_block_floor_outputs` (the manifest's arm value, 8 or 16), read back from EVERY node; a node whose value differs stops the chain.
3. The endpoint sampler as a segment. In run r20261115-1653 it was started by hand at the idle check; run r20261115-1131 had none. The chain starts it right after `deploy12` returns rc 0 and it runs until the chain ends (a stop file or the chain's exit; never `pgrep`), every 60 s, all nodes; its output directory and pid go into the chain's log. A sampler that dies does not stop the chain; the chain says so once.
4. The export check. `orch-prom-export.py`'s check passed series that had a gap (validator-05 between its kill and start is expected; validator-08's and the observer's series that STOPPED mid-run were not). Per node and must-have series: the first and the last sample time inside the run's window, the sample count against the count expected from the scrape interval, and the longest gap; a series whose last sample is more than two scrape intervals before the window's end, or whose longest gap is over a threshold, is listed as `stopped` or `gap` with its times (the killed validator's expected gap is named as expected, from the manifest's chaos times). The check's exit code tells "all whole", "gaps only where expected", "series stopped or missing".
