# N1 — who lacked the block: per under-held header, which voters, by how many outputs and for how long

Common brief: `tasks/bench8/briefs/n-common.md`. Output `benchmark/private/bench8-prep/N1/`. Checkpoint `tasks/checkpoint-bench8-N1.md`.

Question: for every under-held header of runs 7a and 7b in the load blast before the kill (and in 7b's first 817 s), which voters did not hold the named block, how many block-bearing outputs behind the named block was each, and how many seconds passed until that voter's tip reached it? Then the same measure on bench 6's always-on run r20261113-1351 (and r20261113-2118 if you can build its pickle inside your budget), where under-held headers were rare.

Sections:
1. Per run: a table per voter: headers on which it lacked the block, median and p90 deficit in outputs, median and p90 seconds to catch up (from that voter's own tip series; resolution one header interval), share of the under-held headers it is part of.
2. Is it the same few voters all through the window, or does the set rotate? Per 60 s: the set of voters that lacked the block on more than a tenth of that minute's headers. Per under-held header: the count of lacking voters (4 exactly, or more).
3. The deficit's shape: of all (header, lacking voter) pairs, the share 1-2 outputs behind, 3-8, more than 8. A deficit of 1-2 with a catch-up inside one header interval would point at the logged tip's resolution, not at execution.
4. The lagging voters against everything else known about them in the saved analyses: are they the far validators (02, 06), the ones with the slowest disk, the ones that carry more load? One line each with its source; say "not in the saved data" where it is not.
5. Bench 6: the same tables for r20261113-1351, in short.

Decides: the same few voters far behind for minutes → an execution-side cause on those nodes; rotating voters 1-2 outputs behind → an artefact of the logged tip, and run F (floor 16) tests little.
