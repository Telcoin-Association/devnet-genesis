# B8-7 — two more lines: when the order hold releases a lane, and when the sub-dag ordering skips a parent

Common brief: `tasks/bench8/briefs/b8-common.md`. Skills: `tn-domain-consensus`, `tn-domain-worker`. Worktree `/home/drtnarg/coding/telcoin/tn-b8-bench` (after B8-4: start from the tip). Checkpoint `tasks/checkpoint-bench8-B8-7.md`.

Both come from the no-run analyses of bench 7.

1. **`order hold released`** (target `consensus::metrics`). Bench 7 logged the hold only when a header was built (`held`, `held_lanes`, `blockers` on `header proposed`); how long a lane stayed held and what released it could not be read. Read `crates/consensus/primary/src/order_hold.rs` (the module doc says a held lane is released when its blockers leave the tracked set: a cancel report re-queues them, a commit notice commits or re-queues them, or the epoch's proposer is dropped) and where the proposer calls it. Add one line per release of a blocker (one per own header leaving the tracked set while it held at least one lane, not one per digest): `epoch`, `round` (the blocker's round), `lanes` (how many lanes it held), `digests` (how many queued digests became free), `waited_ms` (since that header was proposed), `cause` (`cancel`, `commit`, `requeue_on_commit`, `epoch_end`: use the causes the code has and list them). With `digest_order_hold` off nothing is tracked, so nothing is logged (test).
2. **`subdag parent skipped`** (target `consensus::metrics`). `crates/consensus/primary/src/consensus/utils.rs` (`order_dag_inner`, near `:58-65` at 91a15e223) skips a parent whose round is at most `last_committed[origin]`. In run r20261115-1653, five certificates of a far validator stayed uncommitted although a committed header named them, each time after a later certificate of the same author had committed first. Add one line when the ordering skips a parent for that reason: `epoch`, `leader_round` (the sub-dag being ordered), `origin`, `round` (the skipped certificate's), `last_committed` (that origin's last committed round). This runs once per parent edge of a committed sub-dag: say how many such lines one sub-dag can produce at worst (bounded by the gc depth times the committee size?) and, if a healthy run would log more than a few per second per node, log only skips of a certificate that was NEVER committed (if the code can tell) or aggregate per sub-dag into one line with a count and the first three (origin, round) pairs: your choice, stated, with the cost.
3. Tests: a unit test for each line's fields on the existing harnesses of `order_hold` and of the ordering (`consensus/utils.rs` tests or the Bullshark tests).

Hand back as the common brief says, with one rendered line of each message, the list of causes, and the worst-case line rate of the second.
