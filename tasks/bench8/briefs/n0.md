## Section B — the data map (`data-map.md`, 200 lines at most)

For each of runs 7a and 7b, and for bench 6's two 20,000-IOPS runs where the same kind of file exists:
1. Every per-header pickle and every event extract N1-N5 can use: path, size, what one record is, every field with its type and unit, how many records. Load each once with a small script that prints the type, the length and the keys of the first record (never the data).
2. Which fields exist per VOTER per header (the voter's tip when asked, when it answered, how long it waited, whether it held the named block, the distance in outputs): these carry N1 and N2. Say exactly how "held" and the wait are derived.
3. What marks a header as held by the own-chain order hold or carrying held digests, if anything does (N3 needs "held against not-held"): field name, or "not in the saved data" and which raw log line carries it (`grep -c` it in one node's prefiltered log to prove it exists).

5. Whether a header's parents, or anything from which "which round r certificates a round r+1 header named" can be rebuilt, is in any extract or raw log (N5): e.g. a `parents` count on `header proposed`, certificate-received lines with rounds, the committed sub-dag's contents. List what exists with one sample line each (cut to 220 characters).
6. The windows: name, UTC bounds, per run. The kill and start times of validator-05. The far validators (02 and 06) and how "far" was decided.
7. The scripts under `A3/scripts/`, `A2/scripts/` (and A9/A10) worth importing: one line each on what it reads and writes.
8. Traps: anything a unit would get wrong (validator-05's stand-in tip after the kill, block-bearing outputs against consensus numbers, clock offsets between nodes, eight-voter headers).
