## Why

The stack's fix for #1804 makes a proposer name an execution block that a quorum of its parents' authors already hold, which can be below its own tip. Until this branch the stack had `test_mixed_switch_fleet_is_one_chain` (`git show 500e21afa:crates/e2e-tests/tests/it/exec_block.rs`, from `:520`; `MIN_MIXED_OLDER_CERTIFIED` near `:530`, `check_mixed_fleet`, `assert_header_policies`): two validators ran the fixes and two did not, and it asserted that the fleet is one chain AND that at least a minimum of certified headers of a fixed validator named an older block, which needs a vote from a validator without the fixes. The switches are gone, so that test was deleted. Its stated replacement, `make test-upgrade` (`crates/e2e-tests/tests/it/upgrade.rs`: four validators upgraded in place from a previous binary, `TN_BIN_PATH_PREV`), slows no node and reads no `exec_basis`: all four execute in step, an upgraded proposer names its own tip almost always, and nothing asserts that a previous-binary voter ever voted for a header naming an older block.
Your test puts that assertion back, with binaries in the place of switches.

## The test

A new `#[ignore]` test in `crates/e2e-tests/tests/it/upgrade.rs` (same gating as the existing one: it needs `TN_BIN_PATH_PREV` and skips with the same warning without it; it must be picked up by `make test-upgrade`: read how the Makefile target near `:425-428` selects tests and name yours so that it runs there; say if the target's filter needs no change):
- Four validators from one genesis: two on PREV, two on CURRENT (reuse the module's `TestBinary` / committee helpers; if the harness can only START everyone on PREV, upgrade two in place first with the module's own upgrade helper and take the mixed committee as your starting point).
- Make the PREV validators execute late, so that a CURRENT proposer's quorum value falls below its own tip: the engine's test hook `TN_TEST_EXECUTION_DELAY_MS` exists on upstream `main` too (`git show 0554efd4f:crates/e2e-tests/tests/it/restarts.rs | grep -n 'EXECUTION_DELAY' | head`; this tree: `fleet.rs` `EXECUTION_DELAY_ENV`, `SLOW_EXECUTION_DELAY_MS`). Read how the deleted mixed test and `exec_block.rs`'s kept test slow a node and what delay they use; a PREV binary must be given the variable through its process environment at start. Check that the previous binary honours it: it is built by `make build-e2e-bin-prev` (read the target: same cargo features as the current e2e binary?). If the previous binary cannot be slowed, slow one CURRENT validator in a 1 PREV + 3 CURRENT committee instead (two slow of four still pull the quorum value down; the PREV voter then votes on headers naming an older block) and say why you chose it.
- Drive the module's light load across at least one epoch boundary.
- Assert, with the mixed committee: (1) every validator serves the same blocks (the module's `block_roots` comparison); (2) on a CURRENT validator's log, at least a minimum number of `header proposed` lines with `exec_basis` other than `tip` belong to headers that were certified (`exec_block.rs`'s `HeaderWindow` parsing shows how to join `header proposed` with the certified mark: reuse or copy the minimum needed); (3) for the 2 + 2 committee a certificate needs three of four votes, so each such header carries at least one PREV vote: say this in the test's doc; if you can read the voters from a log line, assert it, otherwise the quorum arithmetic is the argument; (4) no fatal log line, no execution canary line (the constants `FATAL_LOGS`, `CANARY_LOG` in `fleet.rs`).
- Choose the minimum (the deleted test's `MIN_MIXED_OLDER_CERTIFIED` and its reasoning are the model) so that the test fails if the CURRENT proposers named their tip throughout, and passes with margin otherwise; write the reasoning in the constant's doc. You cannot run the test: the orchestrator runs it (three times). So keep timeouts generous, poll for conditions instead of sleeping fixed times, print a one-line summary of what was measured (headers, non-tip certified, per validator) before asserting, and say in your hand-back which assertion you are least sure of.
