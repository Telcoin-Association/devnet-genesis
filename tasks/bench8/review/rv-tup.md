## Answers to the seven questions

1. **Quorum arithmetic: holds.** Threshold = 2·4/3+1 = 3 over equal voting power (committee.rs:476-491, :988-990), so stake plays no part. The author's own vote is appended first (certifier.rs:382-384). The only `quorum reached` line that has `quorum_threshold` is the `VotesAggregator`'s (votes.rs:61-81), and it is used only in `Certifier::propose_header`, so it is always the author's own header. certificates.rs:93 is a trace line without that field, and the test filters it out. Within one author's log, `(epoch, round)` can only match that author's own header: one header per round, and this test has no restart.
2. **`exec_basis`: right in practice, but the wrong field to read.** See M1. Count `exec_tip > exec_block`.
3. **main's voter: nothing refuses or holds an older block.** handler.rs is identical at 33b727fce and 0554efd4f. Its `wait_for_execution(header_block)` (handler.rs:1456-1500) is bounded by `VOTE_EXECUTION_WAIT` = 1 s (config consensus.rs:459). It refuses for good only on a hash mismatch (`Fork`) or a block below the restore floor (`BelowFloor`). A block above the voter's own tip returns `NotYet`, then a recoverable `ExecutionBehind`, and the requester asks again. A block at or below the tip returns `Match`. The test would see nothing more than up to 1 s of delay from the slower PREV voter.
4. **Stability: plausible; timeouts are bounded and fail loudly.** The named block is the third-highest of {own tip, the other CURRENT node's value, the two PREV values}, which is the higher PREV value. The PREV node that named it holds it, so 2 CURRENT votes plus that PREV vote always hold the named block. The delay is 1750 ms against a commit interval of about 1.8 s (fleet.rs:37-45), so the lag stays at 1-2 outputs, below the floor of 8. Under LightLoad every 1.8 s interval carries about 2.4 transfers, so nearly every output has batches and is delayed. If the lag ever passed the floor, CURRENT headers would stop certifying and rounds would stall; the 60 s epoch wait would then fail the test, not pass it falsely. Timeouts and what each waits for:
   - `READY_TIMEOUT` 90 s per node: RPC up, plus a `web3_clientVersion` check against the binary's sha.
   - `wait_for_node_mode` 30 s: the node reaches `CvvActive`.
   - `assert_epoch_reached` `EPOCH_DURATION*6` = 60 s: epoch `closing+1` begins (`EPOCH_SECS` = 20).
   - `assert_epoch_records_verify` 60 s: every node, slow PREV included, serves the closed epoch's record and has executed its final block.
   - Measurement: 180 s, polled every 2 s.
   - `CATCH_UP_SECS` 90 per node: all nodes reach the common head.
   - `RPC_REQUEST_TIMEOUT` per RPC call during the block comparison.
   - nextest slow-timeout: 720 s ×3.
5. **Shared code: no change.** `diff 57a55b221 0a70b58f5 | grep '^-'` shows only the two import blocks. `cross_epoch_boundary` uses `nodes[1]` as its reference, which is CURRENT validator-2 here; that works. Both binaries inherit the fork pins from the make environment. The log directories differ (`upgrade_prev_votes` vs `upgrade`). `setup_log_dir` truncates its files (lib.rs:1049-1050), so no stale lines are read, and the e2e test group runs with max-threads = 1 (.config/nextest.toml:22-27). The one rolling-only assumption is `log_tail` (L1). The BLS passphrase is "restart_test" on both sides.
6. **Conventions.** `HeaderWindow` cannot be used as it stands: the method this test needs was deleted, so restore it (M1). The skip message is clear, but under `make test-upgrade` the Makefile convention calls for failing, not skipping (H1). Docs and commit message: see the last Low row. The commit message has no attribution.
7. **What a `tn-write-e2e` reviewer checks: nothing would be refused.**
   - Every wait is bounded, and the measurement polls.
   - The RPC port is dynamic (:1257); the other ports come from the shared config.
   - `ProcessGuard` holds all four nodes.
   - `LightLoad` aborts on drop (:645-647), including on early returns.
   - On error the datadirs are kept and the path is reported.
   - The log directories do not collide.

## What the PR may claim (after H1 and M1, three passes)

"With `TN_BIN_PATH_PREV` built from main (0554efd4f), each of three runs of `test_upgrade_prev_voters_certify_older_block` certified at least ten headers from this tree's two validators whose `exec_block` was below their own `exec_tip`. Votes are equal-weight in a 2+2 committee and a certificate needs 3 of 4, so each of those certificates includes a vote from a validator running main's binary. All four validators then served identical blocks from genesis and logged no fatal or canary line."
