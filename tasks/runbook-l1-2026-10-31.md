# Runbook: devnet launch 1, 2026-10-31 (as run)

This is a delta to `tasks/runbook-reset-2026-10-30.md`. That runbook's §0 (session prerequisites)
and §1 (image push and probes) still apply. Its §5 recovery and §6 staking are copied in below and
adapted. Four things are different today:

- node 2 moves from Sydney to Dallas;
- the node 5 key comes from a script;
- the release is signed before any node starts;
- the deploy is agent-driven with stdin closed, so it runs in three segments with two operator
  pauses between them.

Nothing below had been run when this was written. Steps marked DESTRUCTIVE delete the fleet.

## Conventions

- Host: xerxes, repo root. "Laptop" means the machine with the YubiKey.
- Every deploy segment runs with `</dev/null` and logs to `logs/deploy-<UTC stamp>-from<N>.log`
  (logs/ is gitignored). `tee` would hide the exit code, so each command prints `rc=` from
  `PIPESTATUS`.
- Commits carry no Co-Authored-By or other attribution lines.
- "(not confirmed)" marks a name this runbook could not check against code or a live system
  (the txgen metric name, some Prometheus label names). The interfaces of `devnet-validator-key.sh`
  and `devnet-release-sign.sh` were checked against their headers as they stood on disk when this
  was written (before the Wave 2 review).
- The interactive helpers come from `devnet-lib.sh`, which sources config.sh. The scripts re-read
  config.sh on every run; your shell does not. Re-source after the zone edit in §3.

```
cd /home/drtnarg/coding/telcoin/devnet-genesis
source ./devnet-lib.sh                        # tn_iap_ssh, tn_node_meta_get, INSTANCE_NAMES, ZONES
TNC=/home/drtnarg/coding/telcoin/tn-cli-dev
RPC=https://rpc.devnet.telcoin.network
stamp() { date -u +%Y%m%dT%H%MZ; }
gcloud auth print-access-token >/dev/null     # fresh reauth window before each long segment (lesson 2026-10-07)
```

## 3. Zone move: node 2 from Sydney to Dallas

and reserves by name in that region. With `ZONES[1]=us-south1-a`, deploy step 1 reserves a NEW

The Sydney address and the Sydney LB group would otherwise stay behind. setup-load-balancer.sh
would create a second `devnet-rpc-ig-2` in us-south1-a and attach it next to the empty Sydney group,
because its attach check matches `zones/<zone>/instanceGroups/<name>`. That leaves a backend that
can never be healthy.

## 4. Deploy in three segments

Step 4 is a manual pause (`read -p`). With stdin closed it prints the DNS map and exits 1 with

again around the signature gate at step 8:

| Segment | Flags | Runs | Stops at | Expected rc |
|---|---|---|---|---|
| D1 | `--yes` | 1-3 | step 4 (DNS pause) | 1 |
| D1b | `--yes --only 12` | 12 | end | 0 |
| D2 | `--yes --from 5` | 5-7 | step 8 (`RELEASE_SIG_PENDING`) | 3 |
| D3 | `--yes --from 8` | 8-16 | end | 0 |

### D1b (added by U7, not in the plan): VPC consensus rules before any node starts
setup-firewall.sh (step 12) limits consensus UDP 49590/49594 to the live /32s of the five nodes,
for both ingress and egress. It last ran when node 2 was at 34.40.150.166. If it waits until
step 12, the VPC drops node 2's new IP from step 8 (first start) until step 12 runs, the whole of
steps 8-11. For that time the genesis committee runs on nodes 1, 3 and 4: exactly quorum (3 of 4),

The script reads live IPs, is idempotent and needs only the instances, so run it now. Step 12 in
D3 re-runs it as a no-op reconcile.
```

    --format='value(sourceRanges,destinationRanges)' | tr ';\t' '\n\n')"
  printf '%s new=%s old=%s\n' "$rule" \
    "$(grep -c -x -F "${NODE2_IP}/32" <<<"$ranges")" "$(grep -c -x -F '34.40.150.166/32' <<<"$ranges")"
done                                                                     # each rule: new=1 old=0

### OPERATOR PAUSE 2: sign the release on the laptop
Copy the one-liner that `prepare` printed in step 6 from the D2 log and run it on the laptop. It
fetches SHA256SUMS from xerxes, signs it on the YubiKey (PIN, then touch) as RELEASE_SIGNER_FPR,
and copies SHA256SUMS.asc back beside it. Its shape, per the script header:
```
# on the laptop: <host> is what prepare printed (xerxes, or RELEASE_SIGN_SSH_HOST)
ssh <host> 'cat /home/drtnarg/coding/telcoin/devnet-genesis/releases/v0.2.0-devnet/SHA256SUMS' > /tmp/SHA256SUMS && \
  gpg --detach-sign --armor --local-user 4E36D35A4AB61B589861D01AC7173F2377CA7573 \
    --output /tmp/SHA256SUMS.asc /tmp/SHA256SUMS && \
  scp /tmp/SHA256SUMS.asc <host>:/home/drtnarg/coding/telcoin/devnet-genesis/releases/v0.2.0-devnet/SHA256SUMS.asc
```
docs/release-signing-ceremony.md ("Path 1: sign on the laptop") has the ceremony and the checks to
make before the touch. Back on xerxes:
```
./devnet-release-sign.sh verify; echo "rc=$?"
```
Expect rc=0 and a `[GNUPG:] VALIDSIG` line, which goes in the verification file. `verify` accepts
only a GOODSIG followed by a VALIDSIG whose last field, the primary key fingerprint, is on the
allow-list built from `RELEASE_KEYS_DIR`. Here that is `4E36D35A4AB61B589861D01AC7173F2377CA7573`,
the grantkee.asc key. That primary key carries the signing capability itself, so the first field
should be the same fingerprint. `verify` also re-checks every hash and that IMAGE_DIGEST equals
config.sh's DOCKER_IMAGE.

From here on SHA256SUMS is signed. It covers IMAGE_DIGEST, genesis.yaml, committee.yaml and
parameters.yaml, so rerunning step 5 or 6 changes the sums, while a rerun of step 7 does not.
After a step 5 or 6 rerun, step 6's `prepare` fails with rc 1 ("signs different content"). To
recover, run `./devnet-release-sign.sh prepare --force` (it removes the stale .asc), sign the new
SHA256SUMS (Pause 2 again), and resume with `--from 7`.

### Per-node recovery (10-30 runbook §5, adapted)
devnet-deploy.sh has no per-node selector. When one node fails, fix it, run that node's driver
directly, then resume the deploy past the failed step. Every resume uses
`./devnet-deploy.sh --yes --from <N> </dev/null`, with a log as above.

| Fails at | Fix, then | Resume |
|---|---|---|
| steps 1-3 (D1) | Fix the cause. Serial console: `gcloud compute instances get-serial-port-output <inst> --zone=<zone> --project=tn-devnet` | `--from <N>`. It stops at step 4 again with rc 1, which is expected. |
| step 5, one node | `./devnet-keygen.sh nodeN` | `--from 6`. It stops at step 8 for the signature. |
| step 6 or 7 | fix | `--from 6` / `--from 7` |
| step 8, one node | `./devnet-finalize.sh nodeN`. It runs `verify` first, which passes once the release is signed. | `--from 9` |
| step 8, before any node | rc 3: no signature yet (Pause 2). rc 1 with "signature verification FAILED": wrong or unlisted key, or the sums no longer match the files. | after `verify` is rc 0: `--from 8` |
| steps 9-16 | fix | `--from <N>` |

- Never re-run keygen or finalize for the whole fleet with `--only`. Keygen refuses nodes that
  already have keys, and finalize's gate refuses nodes that already have a unit, so it exits 1.
- If step 5 or 6 re-runs after signing, run `prepare --force`, re-sign, then `--from 7` (see Pause 2).
- After D2 has started, do not resume at `--from 1` through `--from 4`. Step 4 stops the run again,
  and step 3 can time out: the serial-console marker is written once, at first boot, and may have
  rolled out of the buffer.

## 5. After step 16: stake node 5, verify, close out

### 5a. Stake node 5 (10-30 runbook §6)
Wait until node 5 is within 5 blocks of node 1, then stake:
```
for n in 1 5; do printf 'node%s ' "$n"; cast block-number --rpc-url "https://node$n.devnet.telcoin.network"; done
./devnet-stake-node5.sh                        # dry run: preflight + every call it would make
./devnet-stake-node5.sh --yes                  # mint via Safe -> stake -> sync gate -> activate -> watch (3 epochs by default)
./devnet-stake-node5.sh --yes --from-step 6 --watch-epochs 3   # later, if the session ended: just the committee watch
```
- `activate()` in epoch N sets activationEpoch = N+1. Node 5 becomes Active at the close of N and
  can first join the committee at activationEpoch+2 (N+3).
- With 3600 s epochs the `--yes` run blocks for about 4 h: about one epoch until Active, then three
  epochs of committee logging.
- Five eligible validators share four seats, so any single draw can leave node 5 out. Record which
  epochs seat it.

### 5b. Verification file
Write `tasks/verification-l1-2026-10-31.md`. Its header records commits c1-c3, the digest,
NODE2_IP, and the block height and epoch at the time of capture. After that, one line per item
below with the number seen.

`common/observability/obs-vm/docker-compose.yml`.
```
